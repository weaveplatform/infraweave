## 1. How to read the tables

### 1.1 Columns

| Column | Content | Source |
|---|---|---|
| Method, Path | The REST route the specification reference assigns to the operation | `spacelift.openapi.yaml` ([02](02-graphql-to-rest-mapping.md)) |
| GraphQL field | The root field, marked `(Q)` for a query and `(M)` for a mutation, or `on Type` for a field route that reads a field of an object (such as `Stack.runs`) | `x-graphql` of the operation |
| Purpose | The field description from the schema **[G]**; where it is empty, the Bruno request's docs **[B]**; where both are empty, the request name or a hand-written sentence with its own marker | generated, then enriched |
| Notes | The operation's arguments (query parameters and body schema) and return type **[G]**; deprecated input fields **[G]**; the RBAC action and its legacy fallback; the tier gate; restrictions stated in the description; Bruno's Danger Zone and advanced placement **[B]**; then hand-written notes with their own markers | generated, then enriched |

The tables were generated by script from the specification reference and
then enriched by hand. An independent check re-derived every row's method,
path and GraphQL field from the reference
([#23](https://github.com/weaveplatform/infraweave/issues/23)). The tables walk every operation in the reference, so each operation appears exactly
once, in the section of its first tag. Sub-tags are Bruno's sub-folders (the
`x-bruno` path). Operations with no Bruno request are grouped at the end of
each family as "Fields of `Type`" (field routes) or "Root fields with no Bruno
request".

### 1.2 Permissions

Each mutation whose name matches a value of the `Action` enum **[G]**, or
that the drafting script maps by hand, carries
`RBAC <ACTION> [I] by name, fallback <role> [G][D]`. The `[I]` belongs to the
pairing of operation and action: no source publishes which action a mutation
checks, so the pairing is an inference from names and may be wrong. The
action's existence **[G]**, its docs label and its fallback **[D]** are facts.
The fallback is the legacy space role (Reader, Writer, Admin) checked when no
custom role grants the action, taken from the action tables of
<https://docs.spacelift.io/concepts/authorization/rbac-system> **[D]**. Reads need the space `Read`
action (`SPACE_READ`, fallback Reader) on the subject's space **[D]**, which
the tables do not repeat on every query. Section 9 lists the whole catalog.

Two disagreements between the sources apply to this report:
- The schema marks 18 stack-scoped actions "Disabled. Do not use." **[G]**:
  the context and policy attach and detach actions, the AWS, Azure and GCP
  integration actions, `STACK_ROLE_BINDING_*` and `STACK_WEBHOOK_*`. The docs
  still list them all with an Admin fallback **[D]**. The schema is the higher
  source for the enum; which permission the service checks for an attachment
  is *(unverified)*.
- `STACK_SCHEDULED_DELETE_UPDATE` exists in the schema **[G]** but not in the
  docs tables **[D]**, which list only create and delete for scheduled deletes.

### 1.3 Tier gates

`BillingTierFeature` **[G]** names 31 features the account's tier enables
(`tierFeatures` returns the list, report 04). The schema does not say which
operation checks which feature. The tables tag an operation with a feature
when the names line up, written `Tier <FEATURE> [I]`: the pairing is an
inference and may be wrong. The plan named next to it is what the cited docs
page states for the product feature **[D]**, not a statement that the
operation enforces it. Section 10 lists every feature and the operations tagged.

## 2. Stacks

A stack ties a source (VCS integration, `repository`, `branch`,
`projectRoot`) to a vendor, its state, and its configuration of environment
variables and mounted files [[D]](https://docs.spacelift.io/concepts/stack).
`Stack` has 121 fields **[G]**; `StackInput` has 38, covering behaviour flags
(`administrative`, `autodeploy`, `autoretry`, `localPreviewEnabled`,
`protectFromDeletion`, `enableWellKnownSecretMasking`,
`enableSensitiveOutputUpload`), the hook lists (`beforeInit` through
`afterRun`), `runnerImage`, `workerPool`, `space`, `labels` and
`vendorConfig` **[G]**. Report 07 records every setting.

Identity. `stackCreate` takes an optional `slug` **[G]**; the stack's ID is
its slug, and `stackReslug` regenerates it from the current name, which
breaks Terraform resources that reference the old ID **[G]**.

Lifecycle:
- `manageState` (Spacelift's state backend or the vendor's own) is an
  argument of `stackCreate` and not a field of `StackInput`, so it is set
  once at creation **[G]**. Existing state is handed over at creation through
  `stateUploadUrl` and `stackObjectID`, or later through
  `stackManagedStateImport` **[G]**.
- A stack's state mirrors its most recent tracked run, and is `NONE` before
  any run [[D]](https://docs.spacelift.io/concepts/stack).
- `stackDisable` stops new runs; `stackLock` gives one user exclusive use
  until they or an admin unlock it **[G]**[[D]](https://docs.spacelift.io/concepts/stack/creating-a-stack).
- `stackDelete` optionally destroys resources first; a scheduled delete does
  the same at a set time **[G]**[[D]](https://docs.spacelift.io/concepts/stack/scheduling).

`StackState` **[G]**:

| Value | Description [G] |
|---|---|
| `NONE` | No tracked run has been started yet, so the stack has no meaningful state. |
| `INITIALIZING` | The current tracked run is now initializing. |
| `PLANNING` | The current tracked run is now planning. |
| `FAILED` | The last tracked run has failed. |
| `FINISHED` | The last tracked run has finished successfully. |
| `UNCONFIRMED` | The current tracked run is awaiting human confirmation. |
| `DISCARDED` | The last tracked run has been discarded by the user. |
| `CONFIRMED` | The current tracked run has been confirmed by the user. |
| `APPLYING` | The current tracked run is now applying. |
| `STOPPED` | The last tracked run has been stopped. |
| `DESTROYING` | The current destroy job is now deleting all managed resources. |
| `PREPARING` | The current tracked run is now preparing for execution. |
| `PREPARING_APPLY` | The current tracked run is now preparing to apply the change. |
| `REPLAN_REQUESTED` | The current tracked run is pending a replan. |
| `PREPARING_REPLAN` | The current tracked run is being prepared to be replanned. |
| `READY` | The current tracked run is now ready for execution. |

## 3. Runs

A run is one execution of a stack's workflow on a worker: a tracked run
(deployment), a proposed run (preview), a task (one-off command), a module
test run, a destroy run or a parse run (`RunType`) **[G]**. Spacelift
serializes state-changing work per stack: tracked runs and tasks take an
exclusive lock and block one another, and the blocking run is what
`runConfirm` and `runDiscard` act on when no run ID is given [[D]](https://docs.spacelift.io/concepts/run) **[G]**.
Report 08 records the state machine.

Lifecycle, in brief [[D]](https://docs.spacelift.io/concepts/run):
- `QUEUED` until the stack lock and dependencies allow it, then `READY` for a
  worker; `PREPARING`, `INITIALIZING`, `PLANNING`.
- A tracked run with changes stops at `UNCONFIRMED` for a person or an
  approval policy; `CONFIRMED` then `APPLYING`; terminal `FINISHED`.
- Terminal states are `FINISHED`, `FAILED`, `CANCELED`, `DISCARDED`,
  `STOPPED` and `SKIPPED`.
- A run that has not ended within 30 days of creation is moved to a terminal
  state, with shorter limits for unattended `READY` (two or seven days),
  `UNCONFIRMED` (seven days) and confirmed runs (seven days).

Runs are addressed under their stack (`/stacks/{stackId}/runs/{runId}`) for
every mutation, because the GraphQL mutations take `stack` and `run`
together **[G]**; `run` and `runStack` read one by ID alone **[G]**. Logs are
paged by a token per run state (`Run.logs`), not streamed **[G]**.

## 4. Contexts

A context is a reusable, space-scoped bundle of environment variables,
mounted files and hooks that is attached to stacks and modules
[[D]](https://docs.spacelift.io/concepts/configuration/context). `ContextInput`
carries `name`, `description`, `labels`, `space`, `hooks`, and inline
`stackAttachments` and `configAttachments` **[G]**, so the V2 create and
update can set attachments and elements in one call; `contextUpdateV2`
applies `configAttachments` only with `replaceConfigElements: true` **[G]**.

Attachment:
- Explicit: `contextAttach` with a `priority`; contexts on a stack are
  ordered lowest priority first, and stack-level values override any context
  [[D]](https://docs.spacelift.io/concepts/configuration/context).
- Automatic: a context label `autoattach:<label>` attaches it to every stack
  and module carrying `<label>`; auto-attached contexts have no priority and
  sort alphabetically after explicit ones [[D]](https://docs.spacelift.io/concepts/configuration/context).

A configuration element (`ConfigInput`: `id`, `type`, `value`, `description`,
`writeOnly`, `fileMode`) is a variable or a file (`ConfigType`) **[G]**.
Report 13 records precedence and masking.

`ConfigType` **[G]**:

| Value | Description [G] |
|---|---|
| `ENVIRONMENT_VARIABLE` | Environment variable. |
| `FILE_MOUNT` | File mounted in the workspace. |

## 6. Spaces

A space is a node in the account's tree that holds stacks, policies,
contexts, modules, worker pools and cloud integrations; every account starts
with `root` and `legacy` [[D]](https://docs.spacelift.io/concepts/spaces).
`SpaceInput` has `parentSpace`, `name`, `description`, `inheritEntities` and
`labels` **[G]**. Access granted on a space propagates down the tree, and a
space with `inheritEntities` reads the attachable resources of its ancestors
[[D]](https://docs.spacelift.io/concepts/spaces/how-access-works).

Lifecycle and limits:
- Only root admins change the tree, unless the account lets non-root admins
  manage their own subtrees (`accountToggleAllowNonRootAdminSpaceCreation`,
  report 04); spaces made by non-root admins always inherit [[D]](https://docs.spacelift.io/concepts/spaces/allowing-non-root-admins-to-manage-spaces).
- A space can be deleted only when empty, and `root` and `legacy` never
  [[D]](https://docs.spacelift.io/concepts/spaces/creating-a-space).

The tag also holds the "who can reach this space" queries (users, IdP
groups, API keys, live sessions, stacks), the attachable-resource listings
used by the UI's attach pickers, and the account metrics queries **[G]**.
Report 14 records the access model.

`SpaceAccessLevel` and `StackAccessMode` **[G]**:

| Value | Description [G] |
|---|---|
| `NONE` |   |
| `READ` |   |
| `WRITE` |   |
| `ADMIN` |   |

| Value | Description [G] |
|---|---|
| `RESIDING` | Only stacks whose home space is the queried space. |
| `ALL_WITH_ACCESS` | Every stack that can act in the queried space: residents, ancestor residents (implicit self-read propagates down), inheriting-descendant residents (read propagates up), and explicit binding holders. |

## 7. Worker pools

A private worker pool is a set of workers the customer runs, which take runs
for the stacks and modules assigned to the pool; the public pool is
Spacelift's own [[D]](https://docs.spacelift.io/concepts/worker-pools).

Lifecycle:
- Create with a certificate signing request (`workerPoolCreate`); workers
  start from the pool's config token (`WorkerPool.config`) and private key
  **[G]**[[D]](https://docs.spacelift.io/concepts/worker-pools).
- `workerPoolReset` issues new credentials; workers using the old token can
  no longer connect **[G][D]**.
- `workerPoolCycle` tells every worker to exit; `workerDrainSet` stops one
  worker taking new runs **[D][B]**.
- `driftDetectionRunLimit` and `preparingTimeoutSeconds` tune the pool
  **[G]**; `managedByK8sController` marks a pool owned by the Kubernetes
  operator **[G]** (report 06).

Workers report `WorkerStatus` **[G]**; the queue view and run priorities are
in report 10.

| Value | Description [G] |
|---|---|
| `IDLE` |   |
| `BUSY` | Worker is currently processing a worker. |
| `DRAINED` | Worker is not accepting new work. |

## 8. Modules

A module is a stack-like project that publishes versions of a Terraform or
OpenTofu module to the private registry; it has its own source, worker pool,
contexts, policies and cloud integrations, and runs test cases from
`.spacelift/config.yml` [[D]](https://docs.spacelift.io/vendors/terraform/module-registry).

Lifecycle:
- `moduleCreate`, then versions are created by tracked changes that pass
  their tests, by `versionCreate` (commit SHA or branch head), or by
  `versionPush` from a tarball URL **[G][D]**.
- A successful version number cannot be reused **[D]**.
- A version with no test cases is marked good at once **[D]**.
- `versionYank` marks a version bad, which stops new consumers downloading
  it and cannot be undone **[G][D]**.
- `moduleDelete` needs no active versions **[G]**.
- `moduleShare` shares with other accounts or spaces; `modulePublish` makes
  the module public **[G]**.

`VersionState` **[G]**:

| Value | Description [G] |
|---|---|
| `ACTIVE` | The version is active and can be used. |
| `PENDING` | The version is currently being tested. |
| `FAILED` | Testing the version failed. |

Report 15 records the registry protocol and sharing.

## What this means for infraweave

- The deployment core is 213 operations across seven families, plus the
  stack, run, module, policy, context and worker pool field routes; every
  one needs a REST route, a permission check and a test.
- Permission checks follow a fixed catalog of 150 actions with a legacy
  fallback role per action; the API must expose the catalog so roles can be
  built from it.
- Several mutations act on "the blocking run" when no run ID is given, and
  run mutations are scoped to a stack; the REST surface has to keep both
  shapes.
- Tier gating is a per-feature switch (`BillingTierFeature`), separate from
  RBAC; the plan must decide how infraweave represents features a
  self-hosted install always has.
- Two-step flows (state upload then import or create; local workspace
  upload then proposed run) need pre-signed URL support in the object store.
