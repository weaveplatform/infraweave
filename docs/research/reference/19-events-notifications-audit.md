## 2. The notification inbox

The inbox shows problems Spacelift hit while talking to other systems, such as VCS providers, cloud
providers and Slack **[D]** [notifications][d-notif]. Only admins can see notifications, either for the
whole account or filtered to one stack. The documented categories are VCS provider issues and private
worker usage running into a contracted limit. Notifications are kept for 14 days **[D]**
[notifications][d-notif].

Internal errors reach the inbox even when no notification policy exists; a policy can rewrite their
title, body and severity, or create new inbox entries **[D]** [notification policy][d-np]. Worker
usage events are the opposite: an account without a notification policy receives nothing from them,
and a policy must route them to the inbox, Slack or a webhook **[D]** [worker usage][d-wu].

## 3. The notification policy

The notification policy is a space-level policy of type `NOTIFICATION` that filters, routes and
rewrites notifications. It needs no attachment to a stack, and every notification passes through it
**[D]** [notification policy][d-np]. Rules that match nothing cause no action. Report 09 covers how the
policy is evaluated; this section covers what it receives and what its rules produce.

### Which space's policies run **[D]** [notification policy][d-np]

| Event | Policies evaluated |
|---|---|
| Run updated | policies in the run's space, including those inherited from other spaces |
| Internal error | policies in the root space, unless the error concerns a component whose space can be determined; then that space and the spaces it inherits from. Components are checked in the order stack, worker pool, AWS integration, policy |
| Module version updated | *(unverified)*: presumably the module's space [I] (the input carries `module_version.module.space`) |
| Worker usage | *(unverified)*: presumably the root space [I] (the event is account-wide) |

The policy also always verifies that its space can access whatever the evaluated action concerns
**[D]** [notification policy][d-np].

### Input documents **[D]** [notification policy][d-np]

The docs name the `NOTIFICATION` entry of
`https://app.spacelift.io/.well-known/policy-contract.json` as the most current schema **[D]**
[notification policy][d-np]. Where the page and the contract differ below, the contract wins, and the
difference is stated. In the contract each evaluation carries exactly one event object: `run_updated`,
`internal_error`, `module_version` and `worker_usage` exclude one another **[D]** [policy contract][d-contract].

| Top-level key | Present for | Content |
|---|---|---|
| `account` | every event | `name` |

| `run_updated` | a run changed state | `state`, `username`, `note`, `run`, `stack`, `timing`, `urls`; the contract adds `policy_receipts` and `plan_policy_decision` (`deny`, `warn`, or null) at this level **[D]** [policy contract][d-contract] |
| `internal_error` | an internal error occurred | `error`, `message`, `severity` (`INFO`, `WARNING`, `ERROR`) |
| `module_version` | a module version changed | `module`, `version` |
| `worker_usage` | daily, once usage reaches 60% of the contracted limit or the burst budget | the figures in the table below |

### Rules and their parameters **[D]** [notification policy][d-np]

| Rule | Parameters | Effect |
|---|---|---|
| `inbox` | `title`, `body`, `severity` (all optional) | Creates an inbox notification |
| `slack` | `channel_id` (required), `message`, `mention_users`, `mention_groups`, `thread_key` | Posts to a Slack channel |
| `webhook` | `endpoint_id` (required; a named webhook's ID), `headers`, `payload`, `method` | Sends an HTTP request through a named webhook |
| `pull_request` | `id` (an integer in the contract), `commit`, `branch`, `body`, `deduplication_key` (all optional); the contract adds a boolean `truncate_body` that the page does not describe **[D]** [policy contract][d-contract] | Comments on pull requests |

Behaviour of each route:
- **Slack threading.** Without `thread_key`, Spacelift sends one default message per run and edits it on
  every update. With `thread_key`, the first message starts a thread and every later state change
  is a reply. A custom `message` without `thread_key` is posted as a new message on every evaluation
  and is never edited **[D]** [notification policy][d-np].
- **Slack identity.** A rule can mention the commit author through
  `run.commit.author_identity.federations["slack-oauth"].id`, present only when the author linked a
  Slack account, or the run creator through `run.creator_session.identity`, absent for runs started by
  pushes, drift detection or schedules **[D]** [notification policy][d-np].
- **Webhook requests.** By default a request carries the verification headers, the event's default
  payload, and method `POST`. `headers` adds headers, `payload` replaces the body with any JSON object,
  and `method` changes the HTTP method **[D]** [notification policy][d-np].
- **Log placeholders.** In any JSON value of a webhook `payload`, and in a pull request `body`, the
  strings `spacelift::logs::initializing`, `spacelift::logs::preparing`, `spacelift::logs::planning` and
  `spacelift::logs::applying` are replaced with that phase's logs. Placeholders in JSON keys are not
  replaced **[D]** [notification policy][d-np]. Size limits on the substituted logs are *(unverified)*.
- **Pull request targeting.** `id` names the PR directly; `commit` asks Spacelift to find the PR for a
  SHA, which can fail with GitHub Enterprise Server or forks; `branch` targets every PR whose base is
  that branch. `run.commit.pull_request_id` exists only under some push policy configurations (report
  09) **[D]** [notification policy][d-np].
- **Comment updates.** A constant `deduplication_key` makes Spacelift edit one comment per PR instead
  of adding new ones; the key is scoped to the PR, so reusing it across PRs is safe **[D]**
  [notification policy][d-np].
- **Internal errors.** Inbox delivery of internal errors happens without any policy **[D]**
  [notification policy][d-np].

Which VCS providers support the `pull_request` route is *(unverified)*; the docs' larger example says
it targets GitHub. Report 11 covers PR comments made by the VCS integrations themselves.

## 4. Slack

### Account integration

An admin who is also a Slack admin connects the account to one Slack workspace through an OAuth2
exchange that installs the Spacelift app **[D]** [slack][d-slack]. Connecting sends nothing by itself;
messages come only from notification policies. To disconnect, the app is removed from the Slack
workspace **[D]** [slack][d-slack]. The Slack management screen lives on the Integrations page **[RN]**
[changelog 2025-10-17][rn].

| Type | Field | Type | Meaning **[G]** |
|---|---|---|---|

| | `teamName` | `String!` | Slack workspace name |
| | `slackEnvironment` | `SlackEnvironment!` | `COMMERCIAL` or `GOVSLACK` |
| `SlackAppConfig` | `clientId` | `String` | Client ID of the Slack app; null when none is configured |
| | `canUpdate` | `Boolean!` | False when the config comes from environment variables |

### Self-hosted Slack app **[D]** [self-hosted slack][d-sh-slack] [slack reference][d-sh-slackref]

Self-hosted installations create their own Slack app, either through the UI (copy the manifest, create
the app, paste its credentials, then authorise) or through environment variables:

| Variable | Slack app field |
|---|---|
| `SLACK_APP_CLIENT_ID` | Client ID |
| `SLACK_APP_CLIENT_SECRET` | Client Secret |
| `SLACK_SECRET` | Signing Secret |
| `GOVSLACK_CLIENT_ID`, `GOVSLACK_CLIENT_SECRET`, `GOVSLACK_SIGNING_SECRET` | The GovSlack app's credentials; flags `--govslack-client-id`, `--govslack-client-secret`, `--govslack-signing-secret`; environment only, restart required |

The manifest declares:
- a bot user;
- the slash command `/spacelift`, with usage hint `subscribe, unsubscribe or help`, posting to
  `https://<domain>/webhooks/slack`;
- the OAuth redirect `https://<domain>/slack_oauth`;
- the bot scopes `channels:read`, `chat:write`, `chat:write.public`, `commands`, `links:write`,
  `team:read`, `users:read`;
- the event subscription `app_uninstalled`;
- interactivity, both at `https://<domain>/webhooks/slack`.

Slack must reach the server over the public internet for slash commands and interactivity. Commercial
Slack and GovSlack can both be configured, but only one integration can be connected at a time; GovSlack
uses the same `/slack_oauth` redirect and routes messages to `slack-gov.com` **[D]**
[slack reference][d-sh-slackref].

### Actions from Slack and their access control

Users in the workspace can confirm and discard tracked runs, which needs write access, and view planned
or applied changes, which needs read access **[D]** [slack][d-slack]. Two mechanisms grant that access:

| Mechanism | How | Source |
|---|---|---|
| Login policy | A login policy evaluated on every Slack read or mutation, with input `request.timestamp_ns`, `slack.channel` (`id`, `name`), `slack.command`, `slack.team` (`id`, `name`), `slack.user` (Slack's user object: `id`, `display_name`, `real_name`, `is_admin`, `is_owner`, `is_primary_owner`, `is_restricted`, `is_ultra_restricted`, `is_stranger`, `has_2fa`, `deleted`, `tz`, `enterprise`, `teams`) and `spaces[]`. The default for Slack requests is deny all; if any login policy fails or denies, the result is deny | **[D]** [slack][d-slack] [login policy][d-login] |
| IAM user and channel grants | A user's Slack ID gives them their web permissions in Slack; a `ManagedUserGroupIntegration` of type `SLACK` grants space access rules to a whole Slack channel | **[D]** [IAM admin][d-iam-admin] **[G]** |

`ManagedUserGroupIntegration` **[G]**: `id`, `integrationName`, `integrationType`
(`ManagedUserGroupIntegrationType`, only value `SLACK`), `accessRules: [SpaceAccessRule!]!` and
`slackChannelID`. Create and update inputs take `integrationName`, `slackChannelID` and `accessRules:
[SpaceAccessRuleInput!]!` (create also takes `integrationType`; update takes `id`). Operations:
`managedUserGroupIntegration(id)`, `managedUserGroupIntegrations(integrationType)`,
`managedUserGroupIntegrationCreate`, `managedUserGroupIntegrationUpdate`,
`managedUserGroupIntegrationDelete`. Report 14 covers `SpaceAccessRule` and the roles behind it. Slack
run confirmation honours custom roles **[RN]** [changelog 2026-06-18][rn].

### Personal Slack links **[D]** [external accounts][d-ext]

A user links a personal Slack account on the External accounts page, which lets policies mention or
DM them. Linking requires the account-level workspace, asks Slack for `users:read`, and fails with a
"no workspace" or "workspace mismatch" error when the workspace is missing or different. Spacelift
stores the Slack user ID and display name (falling back to the full name, or empty if the lookup
fails), revokes the Slack token right after reading the name, and removes every Slack link in the
account when the workspace is disconnected or replaced. The federation key in policy input is
`slack-oauth`.

### Per-stack Slack subscription

`StackIntegrations.slack` returns `StackIntegrationSlack` with `activated: Boolean!` and
`channelNames: [String!]!`, the channels subscribed to a stack or module's events **[G]**. The
`/spacelift subscribe|unsubscribe|help` slash command is the subscription path [I] (from the manifest's
usage hint). The docs do not describe this path and send users to notification policies **[D]**
[slack][d-slack]; what a subscription sends is *(unverified)*.

## 5. Microsoft Teams

Account linking for Teams stores the user's Entra object ID and Microsoft profile name, using the
`openid` and `profile` scopes; it exposes the `microsoft-teams-oauth` federation to policies and does
not deliver any messages **[D]** [msteams][d-teams] [external accounts][d-ext].

Channel notifications use a Teams workflow built from the "post to a channel when a webhook request is
received" template; its URL becomes a named webhook endpoint, and a notification policy formats the
payload **[D]** [msteams][d-teams]. Spacelift's Terraform module creates both. Its source at
`2d7020e58441` shows exactly what it does **[S]**:

| Input | Type | Default | Use |
|---|---|---|---|
| `channel_name` | string | required | Naming only ([variables.tf#L1-L4][s-teams-vars]) |
| `notification_policy_filepath` | string | `null` (the bundled policy) | Custom policy body |
| `space_id` | string | `root` | Space for the webhook and policy |
| `webhook_url` | string, sensitive | required | The Teams workflow URL |

| Resource | Settings |
|---|---|
| `spacelift_named_webhook` | name `MS Teams Integration (<channel>)`, `enabled = true`, labels `["msteams"]`, no secret ([webhook.tf][s-teams-webhook]) |
| `spacelift_policy` | type `NOTIFICATION`, labels `["msteams"]` ([policy.tf][s-teams-policy]) |

The bundled Rego v0 policy ([policy.rego][s-teams-rego]) sends to every endpoint labelled `msteams`:
- **runs** of type `TRACKED` or `TASK` reaching `DISCARDED`, `FAILED`, `FINISHED`, `STOPPED` or
  `UNCONFIRMED` ([L14-L41][s-teams-rego-runs]). The card is an Adaptive Card 1.5 inside a
  `{"type": "message", "attachments": [...]}` envelope, with facts for stack, command (tasks), branch,
  commit, trigger, creation time and space, and for tracked runs the added, changed, deleted and
  replaced resource addresses taken from plan-phase changes;
- **module versions** reaching `ACTIVE` or `FAILED` ([L167-L181][s-teams-rego-mod]), with a table of
  test runs;
- `sample` is true whenever a webhook is produced.

The run URL is built as `https://<account>.app.spacelift.io/stack/<id>/run/<id>`, so the bundled policy
assumes SaaS hostnames [I] (from [L4-L12][s-teams-rego]).

## 6. Named webhooks

### Configuration

A named webhook is a space-scoped HTTP endpoint that notification policies route to **[G]**
**[D]** [webhooks][d-webhooks]. Admins manage them on the Integrations page.

### Secret headers

Secret headers are extra request headers whose values are write-only **[G]**. They are set and removed
separately from the webhook:

| Operation | Arguments | Notes **[G]** |
|---|---|---|
| `namedWebhooksIntegrationSetHeaders` | `id: ID!`, `input: NamedWebhookHeaderInput!` (`entries: [KeyValuePair!]!`, each `key`, `value`) | Adds or replaces headers |

value means a new header resource **[S]**

`DD-API-KEY` (section 9). A policy rule's `headers` add to these per request **[D]**

### Delivery, signatures and retries

| Behaviour | Value | Source |
|---|---|---|
| Default method | `POST` | **[D]** [notification policy][d-np] |
| Signature headers | `X-Signature` carries a SHA-1 and `X-Signature-256` a SHA-256 signature derived from the secret and the payload, by the same mechanism GitHub uses **[D]** [webhooks][d-webhooks]. That both are HMACs keyed by the secret is [I] from the GitHub reference, and the example receiver confirms it for SHA-256 (next row) | **[D]** [webhooks][d-webhooks] |
| Signature format | `sha256=<lowercase hex HMAC-SHA256 of the raw body>` in `X-Signature-256`; Spacelift's own example receiver compares exactly that | **[S]** [events collector function.py L7-L9][s-collector] |
| FedRAMP | Only `X-Signature-256`; `X-Signature` is omitted because SHA-1 is not FIPS-compliant | **[D]** [webhooks][d-webhooks] |
| Retry | With `retryOnFailure`, up to 3 retries on a 5xx response | **[D]** [webhooks][d-webhooks] |
| Auto-disable | After 10 or more consecutive failures the webhook is disabled and the account receives a notification; an admin re-enables it manually | **[D]** [webhooks][d-webhooks] |
| Delivery log | Each delivery is stored with its status code and time; details hold request and response headers and bodies | **[D]** [webhooks][d-webhooks] **[G]** |
| Delivery bodies on self-hosted | Request and response bodies live in the Deliveries bucket (`OBJECT_STORAGE_BUCKET_DELIVERIES`), whose retention is user-configurable with 1 day suggested; Spacelift does not expire those objects itself, so the bucket's lifecycle rule sets how long bodies stay readable (report 24) | **[D]** [object storage][d-sh-objstore] |

signature's prefix for `X-Signature` (`sha1=` by analogy with GitHub [I]), and how long SaaS keeps
deliveries. All are *(unverified)*. With a policy `payload`, the signature covers the body actually sent [I]
(from the GitHub mechanism the docs cite).

`WorkerUsage` **[G]**:

| Field | Type | Meaning |
|---|---|---|
| `cycle` | `WorkerUsageCycle!` | The selected cycle: `cyclesAgo`, `start`, `end` (Unix seconds, end exclusive) |
| `selectableCycles` | `[WorkerUsageCycle!]!` | Newest first, back to the oldest retained cycle or the account or contract start |
| `daily(percentiles: [Int!])` | `[WorkerUsageDailyPoint!]!` | Per day: `day`, `max`, `concurrencyAtContractedPercentileToDate`, `concurrencyAtPercentilesToDate`, `burstMinutesUsed`; up to 5 percentiles in 0 to 100 |
| `concurrencyPercentiles(percentiles: [Int!]! = [75, 90, 95, 99])` | `[WorkerUsagePercentile!]!` | `percentile`, `value`; up to 5, each 0 to 100, in request order |
| `concurrencyAtContractedPercentile` | `Int` | Null without a contract percentile |
| `contractedLimit`, `contractedPercentile` | `Int` | Current contract values, applied to past cycles too |
| `multiAccountContract` | `Boolean!` | Whether other accounts share the limit |
| `burst` | `WorkerUsageBurst` | `budgetMinutes`, `usedMinutes`, `remainingMinutes`; null unless the contract has a limit and a percentile |

`WorkerUsageInput.cyclesAgo` accepts 0 to 5 (null means 0). The rollup keeps the current monthly
partition and the six before it; a cycle that ends before the account or contract started is an error,
and a valid cycle older than the rollup reads as zeros **[G]**.

`RunMinutesUsageInput` is a half-open window `[startTime, endTime)` in Unix seconds that must both be
UTC midnight (multiples of 86400; other values are rejected, not rounded), spanning at most 62 days;
`endTime` is clamped to the start of today, and days older than about 183 days report zero **[G]**.
`RunMinutesUsage` returns the effective `window`, `dailyByRunType` (`day`, `runType`, `minutes`),
`dailyByRunState` (`day`, `runState`, `minutes`) and `totals` (`publicMinutes`, `privateMinutes`).
Run-minutes are the durations between consecutive state transitions, counted wholly on the day the
state began; terminal states contribute nothing; `totals` counts only executing states, so queued time
is excluded **[G]**.

How the worker usage figures are computed **[D]** [worker usage][d-wu]:
- distinct connected private workers are sampled each minute, and idle minutes count as zero;
- the billed figure is the concurrency at the contracted percentile over the cycle's minutes so far;
- cycles are anchored on the contract start day in UTC, and a start day beyond a short month's end is
  clamped to its last day;
- the burst budget is the percentile's complement of the cycle's minutes, for example 5% of 44,640
  minutes, or 2,232, at P95 over 31 days;
- figures stop at the last UTC midnight, and per-minute data is kept six months;
- contracted limits, and so these figures and notifications, apply only to negotiated contracts; a
  self-service subscription has no limit to measure against;
- usage is assessed once a day. A `worker_usage` policy input is produced daily once usage reaches 60%
  of the limit or of the burst budget, on both SaaS and self-hosted. Separately, best-effort emails go to at most five root-space
  admins when the burst budget crosses 80% and 100%, only for IAM-mode accounts.

## What this means for infraweave

- **One event fan-out.** Run state changes, module version changes, internal errors and daily worker
  usage all feed one policy-driven router with four sinks (inbox, chat, HTTP, PR comment), alongside
  per-stack webhooks and the audit stream. The plan needs a single internal event model with
  per-event input documents compatible with the notification policy contract.
- **Inbox semantics.** Grouping by key, occurrence counting, dismissal per item, per group and for all,
  admin-only visibility, a 14-day retention, and a severity and type taxonomy.
- **Outbound HTTP delivery.** Delivery must cover:
  - GitHub-compatible HMAC signatures, with a SHA-256-only mode for FIPS;
  - write-only secrets and secret headers;
  - opt-in retries on 5xx, and auto-disable after 10 consecutive failures, which itself notifies;
  - a persisted delivery log with request and response headers and bodies;
  - per-request header, method and body overrides from policy, and run-log placeholder expansion.
- **Audit trail.** Every resource-changing mutation is recorded with:
  - an actor (a user, an API key with its owner, or an administrative run), the IP and identity ULID;
  - an event type, the affected and related resources, and typed metadata for 61 resource types;
  - search, a retention policy, and one streaming webhook per account that reports its own changes,
    can include run events, and sanitises secrets in the payload.
- **Chat integrations.** Slack needs an OAuth app per installation (manifest, slash command,
  interactivity and events endpoints, GovSlack), threading and message editing, access control for
  Slack-originated actions through login policy or channel grants, and personal identity links.
  Teams and Datadog are pure policy-plus-webhook packages and need nothing beyond named webhooks.
- **Metrics.** A Prometheus surface equivalent to the exporter's 22 series, either native or via an API
  the exporter can read, plus the `usage`, `workerUsage`, `runMinutesUsage` and `metrics` read models,
  with their rollup retention and UTC-day windows.
- **Usage export.** A non-GraphQL CSV endpoint with two aspects, and, if infraweave mirrors
  self-hosted licensing, a table-based JSON export. A self-hosted, open-source product has no vendor to
  report to, so the plan must decide what of this applies.
- **Open conflicts.** Secret rotation on named webhooks, the `WORKER_USAGE` type name, and the default
  payloads for module versions and worker usage need a live capture before they are fixed in a
  contract. The notification input follows the policy contract where it and the docs page differ
  (`policy_receipts` placement, the wider run type and change action enums).
