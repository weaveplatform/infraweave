## 1. Policy types

### 1.1 The `PolicyType` enum

`PolicyType` has 13 values, three of them deprecated aliases [G]. The value and
schema-status columns are generated by script from the snapshot; the docs column
restates the docs pages.

| Value | Schema status [G] | Docs name and status | Purpose (own words) |
|---|---|---|---|
| `ACCESS` | current | Access policy; deprecated, disabled from 2026-05-30, replaced by space access control and login policies [D] access, deprecated | Grants or denies a non-admin user read or write on one stack or module |
| `LOGIN` | current | Login policy [D] login | Decides who may log in, as admin or not, and which RBAC roles they get in which spaces |
| `STACK_ACCESS` | deprecated: use `ACCESS` | none; old name of `ACCESS` | Alias of `ACCESS` |
| `GIT_PUSH` | current | Push policy [D] push | Decides what a VCS push or pull request event does for one stack or module |
| `INITIALIZATION` | current | Server-side initialization policy; deprecated, no end-of-life date announced, replaced by approval policies [D] init, deprecated | Blocks a run or task before it initializes |
| `INTENT` | current | Intent policy [D] intent | Allows, denies or holds for review a resource operation in an Intent project or Infra Assistant Build mode |
| `PLAN` | current | Plan policy [D] plan | Inspects the planned change and fails the run (`deny`) or flags it for review (`warn`) |
| `TASK` | current | Task policy; deprecated, no end-of-life date announced, replaced by approval policies [D] task, deprecated | Blocks a task command before the task run is created |
| `TASK_RUN` | deprecated: use `TASK` | none; old name of `TASK` | Alias of `TASK` |
| `TERRAFORM_PLAN` | deprecated: use `PLAN` | none; old name of `PLAN` | Alias of `PLAN` |
| `TRIGGER` | current | Trigger policy; still available, but stack dependencies are the recommended replacement [D] trigger | Starts tracked runs on other stacks when a blocking run ends, or when a module version is released |
| `APPROVAL` | current | Approval policy [D] approval | Approves or rejects a run or task, from human reviews and run context |
| `NOTIFICATION` | current | Notification policy [D] notification | Routes, filters and rewrites notifications to the inbox, Slack, webhooks and pull requests |

So there are ten current values, three deprecated aliases, and within the ten,
three types the docs deprecate while the schema still lists them as current
(`ACCESS`, `INITIALIZATION`, `TASK`).

The changelog dates the alias deprecations: on 2026-10-20 `STACK_ACCESS`, `TASK_RUN`
and `TERRAFORM_PLAN` were marked deprecated in GraphQL [RN 2026-10-20]. The Terraform
provider still accepts all 13 names, validates them case-sensitively, forces a new
resource when `type` changes, and suppresses the diff when the server answers with the
new name of an alias stored under its old name (`ACCESS`/`STACK_ACCESS`,
`PLAN`/`TERRAFORM_PLAN`, `TASK`/`TASK_RUN`) [S]
[`resource_policy.go#L16-L41`](https://github.com/spacelift-io/terraform-provider-spacelift/blob/c72b9bd2f3c3/spacelift/resource_policy.go#L16-L41),
[`#L87-L108`](https://github.com/spacelift-io/terraform-provider-spacelift/blob/c72b9bd2f3c3/spacelift/resource_policy.go#L87-L108).
This suggests the server already stores and returns the new names for the aliases [I, from the diff-suppress logic].

### 1.2 Deprecated types and their replacements

| Deprecated | Replaced by | Timeline [D] deprecated | How to migrate [D] |
|---|---|---|---|
| `ACCESS` (and alias `STACK_ACCESS`) | Spaces with RBAC roles, assigned by login policies or IAM ([D] migrate-spaces) | Disabled on 2026-05-30 | Move stacks into spaces per team or environment; grant roles per space from a login policy's `roles` rule. | `INITIALIZATION` (server-side) | `APPROVAL`; or the worker-side initialization policy on private workers | Not announced | A policy with one `deny` becomes `reject if <condition>` plus `approve if not reject` [D] migrate-approval |
| `TASK` (and alias `TASK_RUN`) | `APPROVAL` | Not announced | Same `reject`/`approve` rewrite; the input moves as in the table below |

Related deprecations that are not `PolicyType` values:
- The login policy's `space_admin`, `space_write` and `space_read` rules are deprecated
  in favour of `roles` [D] login.
- The stack `administrative` flag was replaced by a Space Admin role attachment on
  2026-06-01, and the flag is always false in policy input since then [D] access.
- The `feature:add_plan_pr_comment` stack label is superseded by notification policies
  with `pull_request` rules [D] <https://docs.spacelift.io/concepts/stack/stack-settings>.
- The RBAC `Action` values `STACK_POLICY_ATTACH` and `STACK_POLICY_DETACH` are marked
  "Disabled. Do not use." [G]; report 14 covers actions.

Disagreements between the sources:
- **`ACCESS` after 2026-05-30.** The docs say access policies are disabled on that
  date, which is before the baseline, yet the deprecated page still describes them
  as working, and neither the schema [G] nor the policy contract [D] contract
  marks `ACCESS` deprecated. Whether Spacelift still evaluates them is *(unverified)*.
- **`INITIALIZATION` and `TASK`.** The docs deprecate both; the schema does not.
  The policy contract defines `TASK` but has no `INITIALIZATION` entry at all
  [D] contract, so its input schema is no longer published. Both top sources rank
  equal; infraweave must treat both types as live but deprecated.

## 2. Policy engine and language

### 2.1 `PolicyEngineType`

| Value | Meaning |
|---|---|
| `REGO_V0` | OPA's pre-1.0 Rego syntax: rule bodies without `if`, partial sets as `deny[msg] { ... }` [D] policy |
| `REGO_V1` | Rego v1 syntax: `if` and `contains` keywords required, stricter semantics; recommended for new policies [D] policy |

- `Policy.engineType` is non-null; `PolicyCreateInput.engineType`,
  `PolicyUpdateInput.engineType` and `PolicySimulateInput.engineType` are optional [G].
  `RunPolicyReceipt.engineType` records the engine each evaluation used [G].
- The provider documents `engine_type` as defaulting to `REGO_V0`, optional and
  computed [S] [`resource_policy.go#L112-L120`](https://github.com/spacelift-io/terraform-provider-spacelift/blob/c72b9bd2f3c3/spacelift/resource_policy.go#L112-L120).
  The API's own default when the field is omitted is not stated in the schema, so
  that it is `REGO_V0` is *(unverified)*.
- The UI's editor has a version selector and a policy can switch versions at any
  time [D] policy, [RN 2025-11-07].
- `policyRuntime { openPolicyAgentVersion }` returns the OPA version Spacelift runs
  [G] [D] policy. The example library's CI pins OPA 0.64.0 and Regal v0.36.1 and runs
  `opa check --strict` and `opa test` [S]
  [`continuous-integration.yaml#L16-L58`](https://github.com/spacelift-io/spacelift-policies-example-library/blob/6ff5edb08bc8/.github/workflows/continuous-integration.yaml#L16-L58).

### 2.2 Language constraints

- Every policy is in `package spacelift` [D] policy.
- Spacelift prepends a generated preamble to each policy: a `result` object naming
  every rule the type may define, `default` values for the boolean rules, and an
  always-false placeholder for each set rule so that it is a set. A policy that
  redefines one of these with another type fails validation and is not saved
  [D] policy ("Policy structure"). The contract's `rules` object per type is the
  machine-readable form of that rule list [D] contract.
- Disabled built-ins: `http.send`, `opa.runtime`, `rego.parse_module`, `time.now_ns`,
  `trace`. Policies cannot read external resources or repository files [D] policy.
  The time is available instead as `request.timestamp_ns` style fields in the input
  (`spacelift.request.timestamp_ns` for plan policies) [D] policy.
- Helper functions [D] policy:

  | Helper | Behaviour | Where |
  |---|---|---|
  | `sanitized(x)` | Returns `x` passed through the same sanitizer used for secrets, so a constant can be compared with a sanitized plan value | All types |
  | `exec(x)` | Runs command `x`, returns an object with `status`, `stdout`, `stderr` | Only worker-side initialization policies on private workers |

- Policies are expected to tolerate new input fields and new event kinds; Spacelift
  reserves the right to add both, and asks authors to check the event type (for
  example `not is_null(input.pull_request)`) before acting [D] policy
  ("Backwards-compatibility").

### 2.3 Evaluation timeouts

| Type | Timeout per policy [D] policy |
|---|---|
| Plan | 45 s |
| Notification | 10 s |
| Push | 10 s |
| All others | 5 s |
| All policies for one event combined | 5 min |

Extra limits:
- Push: a hard 10-minute limit on evaluating every stack's push policies for one
  push or pull request event; past it the event may take no action [D] push.
- Access: evaluating every access policy on every stack for one `stacks` request must
  take under 500 ms or the request fails [D] access.
- Self-hosted makes the timeouts configurable through `POLICY_REGO_TIMEOUT_PLAN`,
  `POLICY_REGO_TIMEOUT_LOGIN`, `POLICY_REGO_TIMEOUT_PUSH`,
  `POLICY_REGO_TIMEOUT_APPROVAL`, `POLICY_REGO_TIMEOUT_TRIGGER`,
  `POLICY_REGO_TIMEOUT_NOTIFICATION`, `POLICY_REGO_TIMEOUT_INTENT` and
  `POLICY_REGO_EVALUATION_COMBINED_TIMEOUT`, each a Go-style duration string such as
  `30s` [D] sh-policy. Report 24 owns self-hosted configuration.

### 2.4 Combining several policies

- Several policies of one type can attach to one stack. Each is evaluated on its own,
  so helper rules and variables never leak between them, and the results are then
  combined; a denial from any one of them wins over allows from the others
  [D] policy ("How it works").
- Per-type combination rules are in section 3. The docs recommend a single login
  policy because merged results surprise people [D] login.

## 3. Rules, outcomes and combination per type

Rule names and types come from the contract's `rules` object for each type
[D] contract, cross-checked with the docs table [D] policy. Every type also accepts
the three common rules in section 5 (`flag`, `reset_flag`, `sample`).

| Type | Rules | Kind |
|---|---|---|
| `LOGIN` | `allow`, `admin`, `deny`, `deny_admin` (boolean); `deny_message`, `team` (string sets); `roles` (object: space slug to role slugs); `space_admin`, `space_write`, `space_read` (string sets, deprecated) | positive and negative |
| `ACCESS` | `read`, `write`, `deny`, `deny_write` (boolean) | positive and negative |
| `APPROVAL` | `approve`, `reject` (boolean); `approve_with_note`, `reject_with_note` (string sets) | positive and negative |
| `GIT_PUSH` | `track`, `propose`, `ignore`, `ignore_track`, `notrigger`, `notify`, `fail`, `allow_fork`, `prioritize` (boolean); `cancel`, `message`, `external_dependency` (string sets); `lock`, `unlock`, `module_version` (string); `priority` (`high`, `normal` or `low`) | positive and negative |
| `PLAN` | `deny`, `warn` (string sets) | negative |
| `TASK` | `deny` (string set) | negative |
| `INITIALIZATION` | `deny` (string set) [D] policy; absent from the contract | negative |
| `TRIGGER` | `trigger` (set of stack IDs); `priority` (`high`, `normal` or `low`) | positive |
| `NOTIFICATION` | `inbox`, `slack`, `webhook`, `pull_request` (sets of objects) | positive |
| `INTENT` | `allow`, `deny` (string sets) | positive and negative |

### 3.1 Login

- Login policies are global: they cannot be attached to stacks, and the provider's
  `spacelift_policy_attachment` documents that an attempt to attach one fails; the
  provider has no client-side check, so the API refuses it [D] login, [S]
  [`resource_policy_attachment.go#L18-L26`](https://github.com/spacelift-io/terraform-provider-spacelift/blob/c72b9bd2f3c3/spacelift/resource_policy_attachment.go#L18-L26).
  They live in the `root` space only [D] <https://docs.spacelift.io/concepts/spaces/access-control>.
- A new, changed or deleted login policy applies to all later logins at once, and it
  ends every active session except the one that made the change [D] login.
- Outcome: `deny` beats everything; `admin` grants account admin and implies login;
  `allow` grants non-admin login; `deny_admin` removes admin but keeps non-admin
  access. If no rule matches, the login is denied [D] login, [D] contract.
- If the account has no login policy, the behaviour equals a policy that allows any
  `session.member` [D] login ("Default login policy").
- GitHub or SSO admins and private-account owners always get admin regardless of
  policies, so a broken policy cannot lock everyone out [D] login.
- API keys are evaluated as virtual users, except an admin key in the root space [D] login.
- `deny_message` never denies by itself. On any denial, explicit or implicit, every
  matching message from every login policy is shown: duplicates removed, sorted,
  joined with semicolons and cut at 1,024 characters with a trailing `...`. Messages
  appear on the login page, in the API key token exchange error, and in the `error`
  of the `account.login_failed` audit event. Denials that happen before any policy runs
  (plan without login policies, or no login policies and a non-member) show no message,
  nor do Slack commands [D] login, [RN 2026-10-14].
- `team` replaces the session's team list when non-empty; the rewritten list is what
  later policies see in `session.teams` [D] login.
- `roles` assigns RBAC roles per space; a logged-in user's roles do not change until
  they log in again, except that a space's creator gets access immediately [D] login.
- Login is the one type that samples by default; `sample := false` opts out [D] contract.

### 3.2 Access (deprecated)

- `write` implies `read`; `deny` removes all access and `deny_write` removes write,
  whatever else matches [D] access.
- Access policies are not evaluated for admins [D] access.
- Must be attached to a stack or module to take effect [D] access.

### 3.3 Approval

- Without an approval policy, anyone with write access to the stack can create and
  proceed with a run or task [D] approval.
- Per policy, the outcome is approve, reject or undecided. Undecided means both
  `approve` and `reject` are false (more reviews needed) or both are true (conflict).
  A non-empty `approve_with_note` or `reject_with_note` set approves or rejects and
  records each note against the decision [D] approval, [D] contract.
- `approve` must be definable for a run to progress; `reject` is optional. A reject
  fails the run at once [D] approval.
- Across policies, a proposed run in `PENDING_REVIEW` finishes only once every
  attached approval policy approves [D]
  <https://docs.spacelift.io/concepts/run/proposed>. That a single reject from any one
  policy fails the run regardless of the others is *(unverified)*, though it follows
  the "denial wins" rule in section 2.4 [I].
- Reviews come from `runReview(stack, run, decision, note)`, with `RunReviewDecision`
  `APPROVE` or `REJECT`, stored as `RunReview` with the run state and `stateVersion`
  at review time [G]. Reviewers need write or admin on the stack. Only a reviewer's
  newest review counts, so a reviewer can change their mind [D] approval. Reviews are
  grouped in the input by the state they were made in (`reviews.current` and
  `reviews.older`), so a review given while queued does not carry over to the
  unconfirmed state [I, from the input shape].
- `Run.needsApproval` and `Stack.needsApproval` expose a pending approval [G].

### 3.4 Push

- One evaluation per stack or module linked to the repository the event comes from
  [D] push. For a module with a project root, a tagged commit that touches no file
  under it skips the module's push policy entirely, with no sample recorded [D] push.
- Outcome order [D] push:
  1. any `ignore` makes the push ignored, whatever else matches;
  2. otherwise any `track` creates a tracked run, unless `ignore_track` is also true,
     in which case `track` is dropped;
  3. any `propose` creates a proposed run;
  4. no matching rule means ignore.
- `notrigger` is read only when `track` is true: the head commit is set but no run is
  created [D] push.
- `notify` (default false) sends a commit status for an ignored push; it cannot
  suppress checks for other outcomes. By default an ignored push sends no check, and
  if one is sent it is `skipped`; `fail` makes it a failure, and `message` replaces its
  text, with entries from all evaluated policies joined by commas [D] push, [D] contract.
- `cancel` lists IDs from `input.in_progress` (runs that are `QUEUED`, `READY` or
  `UNCONFIRMED`) to cancel. Only proposed and tracked stack runs can be canceled, only
  by a new run of the same type, only if the push creates a run, and only best-effort:
  a run picked up by a worker or approved meanwhile is not canceled [D] push.
- `lock` with a non-empty string locks an unlocked stack under that owner key, does
  nothing if the same key holds it, and rejects the run if another key holds it. All
  policies evaluated for the push must agree on the value. `unlock` releases only a
  lock held under the same key [D] push, [D] contract.
- `priority` sets the run's starting priority (`high`, `normal`, `low`); `prioritize`
  is the older boolean equal to `high`. Evaluation fails, creates no run and notifies
  when `priority` has an invalid value, two attached policies disagree, or a policy
  sets both `priority` and a true `prioritize`. Priority only applies on private
  worker pools [D] push. Report 08 covers priorities.
- `module_version` sets the version to publish when the push targets a module [D] push.
- `allow_fork` lets a pull request from a fork run; forks are refused by default
  [D] push. The meaning of `pull_request.head_owner` differs per VCS (GitHub owner,
  GitLab group, Azure DevOps project UUID, Bitbucket Cloud workspace, Bitbucket
  Data Center project key) [D] push; report 11 owns VCS.
- `external_dependency` names markers the created run waits on; see 3.5.
- Deduplication: a push and its pull request event can both produce an actionable
  result. Runs are deduplicated per stack on the key (commit SHA, run type); the first
  event wins, which is why the surviving run often lacks `pull_request_id` [D] push.
- If no push policy is attached, the default behaviour is a built-in policy that
  tracks pushes to the tracked branch that touch the project root or an additional
  project glob, proposes for every affected push or pull request (a push to the
  tracked branch matches both `track` and `propose`), and ignores
  unaffected pushes and all tag pushes [D] push ("Default Git push policy").
- Ignored pushes are recorded as ignored triggers; report 08 lists
  `RunIgnoredTriggerReasonType`, which includes `CUSTOM_POLICY` and
  `CUSTOM_POLICY_NO_TRIGGER` [G], and the docs list the reasons (outside project root,
  tag push, default policy disabled with no custom policy, dismissed by a custom
  policy) [D] <https://docs.spacelift.io/concepts/run/ignored-triggers>.

### 3.5 External dependencies (push)

- A run created by a push policy with `external_dependency` entries stays queued until
  every dependency is `FINISHED` or `SKIPPED`; any `FAILED` dependency fails the run
  with a note [D] ext-deps.
- `Run.externalDependencies` lists `RunExternalDependency { id, status, createdAt,
  completedAt }`; `RunExternalDependencyStatus` is `PENDING`, `FINISHED`, `FAILED` or
  `SKIPPED`; the experimental mutation
  `runExternalDependencyMarkAsCompleted(dependency, status)` completes one [G].
- The caller needs write on every space with a run waiting on that dependency name,
  and names should embed something unique such as the commit SHA [D] ext-deps.

### 3.6 Plan

- `deny` fails the run; messages print in red. `warn` never fails a run; messages
  print in yellow [D] plan.
- On a tracked run with autodeploy, one warning is enough to stop and wait for a
  human (`UNCONFIRMED`) instead of applying [D] plan,
  [D] <https://docs.spacelift.io/concepts/run/tracked>,
  [D] <https://docs.spacelift.io/concepts/stack/stack-settings>.
- On a proposed run, a warning with approval policies attached sends the run to
  `PENDING_REVIEW` [D] <https://docs.spacelift.io/concepts/run/proposed>.
- The docs recommend denying on `PROPOSED` and warning on `TRACKED` [D] plan.

### 3.7 Task and initialization (deprecated)

- Task: any `deny` message stops the task run from being created, and the API call
  returns an error. Blocking admins is advisory only, since an admin can detach the
  policy [D] task.
- Server-side initialization: any `deny` prevents the run or task from initializing
  [D] init. The resulting run state is not stated; that it is `FAILED` is
  *(unverified)*.
- Worker-side initialization: a private worker loads a policy file from
  `SPACELIFT_LAUNCHER_RUN_INITIALIZATION_POLICY`, refuses to start if it does not
  validate, and evaluates it before a run initializes; it may call `exec` and read
  `user_provided_metadata`, which supports signed runs [D]
  <https://docs.spacelift.io/concepts/worker-pools>,
  [D] <https://docs.spacelift.io/concepts/run>. Report 10 owns the worker side.

### 3.8 Trigger

- Evaluated when a stack-blocking run, meaning a tracked run or a task, reaches
  `FINISHED`, `CANCELED`, `DISCARDED`, `STOPPED` or `FAILED` [D] trigger.
- `trigger` names stack IDs to start tracked runs on. Triggered runs evaluate trigger
  policies again when they end, so retry policies must guard against loops [D] trigger.
- A workflow is the first run plus every run it caused directly or indirectly; the
  input's `workflow` lists every run in it, on any stack, which solves "diamond"
  fan-in [D] trigger.
- Attached to a module, a trigger policy also runs when a new version is released,
  and can trigger the stacks that consumed the previous newest version. Only stacks the
  policy can reach (directly or by space inheritance) are affected, and a stack must
  have initialized once before the module tracks it [D] trigger.
- `priority` applies to every stack the policy triggers. A policy without `priority`
  defers to one with it; two policies that disagree leave the run at `normal` and
  notify the author; an invalid value fails the evaluation, triggers nothing, and
  notifies. `input.run.priority` carries the finished run's level [D] trigger,
  [D] contract.

### 3.9 Notification

- Not attached to stacks: a notification policy works at space level. For run
  updates, the policies in the run's space and the spaces it inherits from apply.
  Internal errors use the root space unless the error is about a component whose
  space can be found, checked in the order stack, worker pool, AWS integration,
  policy [D] notification.
- No matching rule means nothing is sent. Error notifications reach the inbox by
  default even with no policy [D] notification.
- Route item shapes [D] notification, [D] contract:

  | Rule | Item fields (required marked *) | Notes |
  |---|---|---|
  | `inbox` | `title`, `body`, `severity` | All optional |
  | `slack` | `channel_id`*, `message`, `mention_users`, `mention_groups`, `thread_key` | Without `thread_key`, Spacelift's default message is one per run and edited in place; a custom message without `thread_key` is a new message every time; with `thread_key` each update is a reply in one thread |
  | `webhook` | `endpoint_id`*, `headers`, `payload`, `method` | Needs a named webhook; defaults are Spacelift's headers and payload with `POST` |
  | `pull_request` | `id`, `commit`, `branch`, `body`, `deduplication_key`, `truncate_body` | All optional; `branch` is the PR base branch; a constant `deduplication_key` updates one comment per PR; `truncate_body` is in the contract only |

- Placeholders `spacelift::logs::initializing`, `spacelift::logs::preparing`,
  `spacelift::logs::planning` and `spacelift::logs::applying` in payload values or
  comment bodies are replaced with that phase's logs; placeholders in JSON keys are
  ignored [D] notification.
- The `worker_usage` event (contracted worker limit) exists since 2026-09-04
  [RN 2026-09-04]. Report 19 owns delivery.

### 3.10 Intent

- Per operation (create, update, delete, import, refresh) in an Intent project or
  Infra Assistant Build mode: allowed when at least one `allow` matches and no `deny`;
  denied when any `deny` matches, with the reasons returned; otherwise pending manual
  review. With no Intent policy attached, every operation is allowed. Several policies
  combine and one `deny` blocks [D] intent.
- `intentPolicyInputSchema` returns the input schema as a string [G]. Report 22 owns
  Intent.

## 5. Flags, flag reset and sampling

### 5.1 Flags

- `flag` is a set of arbitrary strings an evaluation attaches. When the evaluation is
  about a run, the flags go on the run's policy receipt and later policies for the
  same run read them in `run.flags` [D] contract, [D] policy.
- The docs name push, approval, plan and trigger as the types that touch a run and
  so can set flags [D] policy; the contract defines `flag` on all nine types
  [D] contract. What a flag set by a type with no run (login, access, notification,
  intent) does is *(unverified)*.
- Policies of the same type do not see each other's flags; flags pass between
  types [D] policy. They appear in the UI, which makes them useful for debugging
  [D] policy.
- `RunPolicyReceipt.flags` stores them per evaluation [G].

### 5.2 Flag reset

- `reset_flag` lists flags to clear [D] flag-reset.
- A flag can have several owners (every policy that set it). It is removed only when
  every owner asks to reset it, so one policy cannot clear another's flag [D] flag-reset,
  [D] contract.
- Within one evaluation, resets apply first and new flags second [D] flag-reset.
- Policies without a `PolicyULID` (older policies) can set flags but not reset any
  [D] flag-reset. How a policy gets a ULID is *(unverified)*.
- Supported on push, approval, plan and trigger [D] flag-reset. During targeted
  replans, plan and approval policies run several times in one run, and reset lets the
  flags follow the current plan [D] flag-reset; report 08 owns targeted replan.

### 5.3 Sampling

- `sample` is a boolean rule. When true, Spacelift stores the input, the policy body
  at that moment and the result [D] policy. It defaults to false except for login
  [D] contract.
- Sampling a percentage needs a deterministic source of randomness inside the input,
  such as the request timestamp [D] policy.
- Hourly limits: 200 samples for notification policies, 200 for push policies, 500
  shared by all other types [D] policy.
- Retention: the UI shows the 100 most recent evaluations from the last 7 days.
  Session data in samples is kept 7 days. Plan inputs hash string attributes of
  resources, so secrets do not leak through samples [D] policy.
- The workbench and stored inputs are visible only to account admins [D] policy.

## What this means for infraweave

- **Ten live types, three aliases.** The policy store must accept all 13
  `PolicyType` names, normalise the three aliases to their current names, and keep
  `ACCESS`, `INITIALIZATION` and `TASK` working while flagging them deprecated.
- **Two Rego dialects.** Each policy carries an engine version; evaluation needs OPA
  in both v0 and v1 modes, a fixed preamble per type that defines the result object
  and defaults, rejection of policies that redefine those rules with another type,
  the five disabled built-ins, and the `sanitized` helper (plus `exec` only for a
  worker-side initialization policy).
- **Contracts per type.** Input documents must match the contract's JSON Schemas
  field for field, including the per-type run variants, the vendor blocks in plan
  input, custom inputs from `*.custom.spacelift.json`, and the documented null versus
  absent quirk for `terragrunt`. Publishing a contract document is part of parity.
- **Combination semantics.** Each type has its own rule for merging several
  policies (deny wins, ignore wins, all approvals required, disagreeing priorities
  fail or fall back to normal, lock values must agree, login messages sorted and
  capped at 1,024 characters).
- **Hooks into the run state machine.** Push before run creation; approval on
  `QUEUED`, `UNCONFIRMED` and `PENDING_REVIEW` and on each review; plan inside
  `PLANNING` and on each targeted replan; trigger on the five terminal states of
  blocking runs and on module releases; notification on every state change.
- **Flags.** Flags flow between types through the run, with multi-owner reset and
  reset-before-set ordering, and are stored on per-evaluation receipts.
- **Evidence and tooling.** Policy receipts per run, sampled evaluations with hourly
  quotas and 7-day retention, captured inputs with sensitive values removed, a
  simulate endpoint that takes body, input, libraries and engine, and templates.
- **Attachment.** Explicit attachment once per target, `autoattach:<label>` and
  `autoattach:*` scoped by space inheritance, global login policies, space-level
  notification policies, and Intent project attachment.
- **Limits.** Per-type timeouts, a combined per-event budget, the 10-minute push
  ceiling and the access policy 500 ms budget, configurable on self-hosted.
- **Example library.** 67 MIT templates and 61 tests are available as a parity and
  regression corpus.
