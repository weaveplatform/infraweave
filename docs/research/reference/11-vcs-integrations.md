## 2. The common integration model

### 2.1 `VCSIntegration`

Every provider except the built-in GitHub App and Origin shares one envelope **[G]**:

| Field | Type | Notes |
|---|---|---|
| `id` | `ID!` | Unique per account and provider. Empty for `GITHUB` **[G]** |
| `name` | `String!` | Fixed after creation, because the webhook endpoint is derived from it **[D]** [github](https://docs.spacelift.io/integrations/source-control/github) |
| `description` | `String!` | Markdown **[D]** |
| `labels` | `[String!]!` | |
| `isDefault` | `Boolean!` | At most one default per account and provider **[G]** **[D]** |
| `space` | `Space!` | Default integrations always sit in the root space **[G]** |
| `provider` | `VCSProvider!` | |
| `details` | `VCSIntegrationDetails` | Union of the provider objects; returned only to callers with admin access **[G]** |
| `createdAt`, `updatedAt` | `Int!` | Unix seconds |
| `searchUsers(input: SearchInput!)` | `SearchVCSIntegrationUsersOutput!` | Stacks and modules using the integration; each `VCSIntegrationUser` has `stackId`, `stackName`, `isModule`, `spaceDetails` **[G]** |
| `searchUsersSuggestions(input: SearchSuggestionsInput!)` | `SearchSuggestionsOutput!` | |

Each provider object repeats `id`, `name`, `description`, `labels`, `isDefault`, `space` (nullable there) and adds `vcsChecks: VCSCheck!`, `vcsCheckOptions: VCSCheckOptions` and `useGitCheckout: Boolean!` **[G]**.

### 2.2 Shared create and update inputs

Every create mutation except GitHub's and Origin's takes `customInput: CustomVCSInput`; every update takes `customInput: CustomVCSUpdateInput` **[G]**.

| `CustomVCSInput` field | Type | Default | Notes |
|---|---|---|---|
| `name` | `String!` | | Becomes the slug `id` and part of the webhook URL **[D]** |
| `description` | `String` | | |
| `spaceID` | `ID!` | | Must be `root` when `isDefault` is true **[S]** (`terraform-schema.json`, `is_default` on each integration resource) |
| `labels` | `[String!]` | | |
| `isDefault` | `Boolean` | `false` **[G]** | |
| `vcsChecks` | `VCSCheck` | `INDIVIDUAL` **[G]** | |
| `vcsCheckOptions` | `VCSCheckOptionsInput` | | See [section 12](#12-commit-checks-pull-request-comments-and-deployments) |
| `useGitCheckout` | `Boolean` | see below | `false` downloads an archive through the provider API |

| `CustomVCSUpdateInput` field | Type | Notes |
|---|---|---|
| `id` | `ID!` | Slug of the integration |
| `space` | `ID!` | Space after the update; an update can move an integration between spaces |
| `description`, `labels`, `vcsChecks`, `vcsCheckOptions`, `useGitCheckout` | as above | `isDefault` and `name` are not updatable **[G]** |

The default for `useGitCheckout` differs by source. The Terraform provider documents `true` for GitLab and Azure DevOps and `false` for Bitbucket Data Center **[S]** (`terraform-schema.json`, `spacelift_gitlab_integration.use_git_checkout`). Bitbucket Cloud always uses Git checkout, because Bitbucket's archive download does not accept API tokens **[G]** (`BitbucketCloudIntegration.useGitCheckout`). The GitHub page describes Git checkout as experimental and per stack, enabled with the label `feature:enable_git_checkout` or by support **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#webhook-integrations), while every integration form carries a **Use Git checkout** toggle that sparse checkout requires **[D]**. The schema exposes only the per-integration field **[G]**; whether the label has any effect alongside it is *(unverified)*.

### 2.3 Default and space-level integrations

- An account can have one default integration and any number of space-level integrations per provider **[D]** [github](https://docs.spacelift.io/integrations/source-control/github), [gitlab](https://docs.spacelift.io/integrations/source-control/gitlab).
- A default integration is available to every stack and module. A space-level integration can be attached only by stacks and modules in its space, or in a space that inherits from it **[D]** [stack-settings](https://docs.spacelift.io/concepts/stack/stack-settings#vcs-integration-and-repository).
- Space-level integrations are an Enterprise plan feature **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#space-level-integrations).
- Visibility: readers of the integration's space see name, description and labels; only that space's admins see webhook URLs and secrets. A default integration's details are visible only to root space admins **[D]**. The schema enforces this through `details`, which needs admin access **[G]**.
- `attachableVCSIntegrationsForProviderInSpace(id, provider)` lists what a stack or module in a space may attach **[G]** **[B]** (`Spaces/Attachable Resources`).
- A stack or module points at a non-default integration through `vcsIntegrationId`; leaving it empty means the provider's default integration **[G]** (`StackInput.vcsIntegrationId`).
- Deleting an integration in use is allowed. The stack is then marked `vcsDetached: true`, receives no webhooks and cannot be triggered manually until a new integration is chosen; `Stack.vcsIntegration` becomes null **[D]** [gitlab](https://docs.spacelift.io/integrations/source-control/gitlab#consequences) **[G]**.
- Recreating an integration under the same name keeps the webhook URL; for GitLab, Bitbucket Data Center and Azure DevOps the secret still changes and must be updated on the provider side **[D]**.

### 2.4 Binding a stack or module to a repository

| `StackInput` field | Type | Meaning |
|---|---|---|

| `vcsIntegrationId` | `ID` | Non-default integration, see 2.3 |
| `namespace` | `String` | Owner: GitHub organization or user, GitLab group path including subgroups, Bitbucket project or workspace, Azure DevOps project, or a cosmetic label for raw Git **[S]** **[D]** [gitlab](https://docs.spacelift.io/integrations/source-control/gitlab#namespaces) |
| `repository` | `String!` | Repository name without the owner; the slug of the repo for `SPACELIFT` **[S]** |
| `repositoryURL` | `String` | Only for raw Git **[S]** |
| `branch` | `String!` | Tracked branch; must exist before it is set **[D]** [stack-settings](https://docs.spacelift.io/concepts/stack/stack-settings#vcs-integration-and-repository) |
| `projectRoot` | `String` | Directory whose changes affect the stack |
| `additionalProjectGlobs` | `[String!]` | Further globs that affect the stack |
| `gitSparseCheckoutPaths` | `[String!]` | Used only when Git checkout is on |
| `githubActionDeploy` | `Boolean` | Enables the **Deploy** action on GitHub check runs; default `true`. The Terraform provider exposes it as `allow_run_promotion` and deprecates `github_action_deploy` **[G]** **[S]** [resource_stack.go](https://github.com/spacelift-io/terraform-provider-spacelift/blob/c72b9bd2f3c3/spacelift/resource_stack.go#L425-L445) |

`Module` carries the same fields **[G]**. In the Terraform provider each provider is a nested block with `id` (integration, empty for default), computed `is_default`, and `namespace`, or `project` for `azure_devops`; `raw_git` takes `namespace` and `url`; `origin` and `spacelift_repo` take no attributes **[S]** (`terraform-schema.json`, `spacelift_stack.blockTypes`). The blocks are mutually exclusive.

Read-side fields on `Stack` and `Module`: `apiHost` (empty when the integration was removed), `trackedCommit`, `trackedBranchHead`, `trackedCommitSetBy`, `repositoryTags`, `pullRequests` (up to 50 open PRs against the tracked branch), `vcsDetached` and `vcsIntegration` **[G]**. `PullRequest` has `id`, `authorLogin`, `createdAt`, `updatedAt`, `draft`, `headBranch`, `headBranchURL`, `headSHA`, `title`, `url` and `runs` (`run` is deprecated in favour of `runs`) **[G]**. `Commit` has `authorLogin`, `authorName`, `hash`, `tag`, `message` (first line only), `timestamp` and `url` **[G]**.

Repository renames: GitHub renames are followed automatically through the `repository` webhook; GitLab renames must be applied to the stack by hand **[D]** [stack-settings](https://docs.spacelift.io/concepts/stack/stack-settings#vcs-integration-and-repository).

### 2.5 Browsing and testing

| Root field | Kind | Purpose **[G]** |
|---|---|---|
| `vcsIntegrations` | query | All integrations in the account |

| Enum | Values **[G]** |
|---|---|
| `VCSIntegrationTestStatus` | `SUCCESS`, `FAIL` |
| `VCSIntegrationTestType` | `CONNECTION`, `PERMISSIONS`, `WEBHOOK`, `GITHUB_APP_EVENTS` |

The run cap is set under **Organization Settings > Limits**, up to 500; when an event would exceed it, the reason is reported to the VCS as a failure **[D]** [run](https://docs.spacelift.io/concepts/run#limit-runs).

## 3. GitHub built-in app

**Setup.** An account created by signing in with GitHub links GitHub by installing the Marketplace app `spacelift-io` on an organization or user and choosing repositories **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#signed-in-with-github). Installing the app on an account creates the corresponding Spacelift account **[D]** (webhook table). There is no create or delete operation; the integration exists because the app is installed **[B]** (`VCS Integrations/GitHub` folder).

**Settings.** `githubIntegration` returns `GithubIntegration` with `vcsChecks`, `vcsCheckOptions`, `useGitCheckout`, `apiHost` and `isEnterprise` **[G]**. `githubIntegrationUpdate(vcsChecks: VCSCheck!, vcsCheckOptions, useGitCheckout)` is the only write **[G]**.

**Authentication.** GitHub App credentials held by Spacelift; the account owner holds no secret. The app's installation tokens are refreshed through `POST /app/installations/{id}/access_tokens`, as the vcs-agent's GitHub allowlist shows for the custom-app case **[S]** [github_enterprise.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/allowlist/github_enterprise.go#L64-L75) **[I]** (the built-in app is assumed to use the same GitHub App flow).

**Identity and legacy access.** When GitHub is the identity provider, login reads organization and team membership through the GitHub API and stores it in a session token valid for one hour, for use by login and stack access policies **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#legacy-method). Report 14 covers this. The changelog of 2026-07-08 adds linking a GitHub account to a Spacelift identity by OAuth **[RN]**.

**Using several GitHub organizations** requires custom apps ([section 4](#4-github-custom-app-and-github-enterprise)) **[D]**.

### 4.3 Authentication and permissions

Manual setup generates the webhook endpoint and secret in Spacelift first, then the user creates the app on GitHub with them, generates a private key and enters the App ID and key **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#set-up-manually). Spacelift authenticates as the App with the key and acts through installation tokens **[I]** (from `appID` and `privateKey`, and the allowlist's token refresh call).

Repository permissions the app needs **[D]**:

| Permission | Access | Used for |
|---|---|---|
| Checks | Read and write | Run state on commits and PRs; branch protection |
| Commit statuses | Read and write | Commit statuses for branch protection and GHE compatibility |
| Contents | Read | Source download |
| Deployments | Read and write | GitHub Deployments for tracked runs, and their cleanup |
| Metadata | Read | Required by GitHub |
| Pull requests | Read and write | Detecting affected stacks; write only for Spacelift's PR comments |
| Webhooks | Read and write | Receiving events, maintaining the webhook |

Event subscriptions: Check run, Issue comment, Organization, Pull request, Pull request review, Push, Repository **[D]**. The setup step that lists them calls them Organization permissions; they are GitHub webhook event names, so reading them as event subscriptions is **[I]**. The PR comment page adds read access to Issues and the `issue_comment` event for comment-driven actions; the wizard sets them up automatically **[D]** [pull-request-comments](https://docs.spacelift.io/concepts/run/pull-request-comments#pull-request-comment-driven-actions).

The app can be installed on several accounts or organizations, each listed in `installations` **[D]** **[G]**. Deleting the app on GitHub does not delete the Spacelift integration; that is a separate step **[D]**.

### 4.4 Webhook verification

The webhook secret is the GitHub App's webhook secret **[D]**. GitHub signs each delivery with HMAC-SHA256 of the body in `X-Hub-Signature-256` **[I]** (GitHub's documented behaviour; Spacelift's verification code is not public).

Terraform resource `spacelift_gitlab_integration` **[S]** (`terraform-schema.json`): `name`, `api_host` and `user_facing_host` required; `private_token` (deprecated, sensitive) or `private_token_wo` with `private_token_wo_version` (write-only, Terraform/OpenTofu 1.11+); `space_id` (default `root`), `is_default`, `labels`, `description`, `vcs_checks` (default `INDIVIDUAL`), `use_git_checkout` (default `true`); computed `webhook_secret` and `webhook_url`. Data source `spacelift_gitlab_webhook_endpoint` reads `gitlabWebhooksEndpoint` **[S]**.

**Authentication.** A GitLab access token with the `api` scope, because GitLab has no narrower scope that allows writing commit statuses, MR comments and deployments. A user-bound token's user needs Maintainer access on each project. GitLab tokens are personal, so the docs advise a machine user **[D]** [gitlab](https://docs.spacelift.io/integrations/source-control/gitlab#create-an-access-token).

**Webhooks.** One project webhook per repository, however many stacks use it; a second hook on the same repository causes unintended behaviour. URL and secret token come from the integration details. Triggers: **Push events**, **Tag push events**, **Merge request events** **[D]** [gitlab](https://docs.spacelift.io/integrations/source-control/gitlab#set-up-webhooks). GitLab sends the secret in the `X-Gitlab-Token` header **[I]** (GitLab's documented behaviour). The docs suggest creating hooks with GitLab's own Terraform provider **[D]**.

**Feedback.** A push or tag event may trigger runs whose status appears as GitLab pipelines with one job per Spacelift run; every merge request affected by the commit gets a comment with the change; each stack has a GitLab Environment that records its tracked runs **[D]** [gitlab](https://docs.spacelift.io/integrations/source-control/gitlab#spacelift-in-gitlab).

## 9. Raw Git

Raw Git (`GIT`) builds a stack or module from any publicly reachable Git URL, including a GitHub gist, with no integration object **[D]** [raw-git](https://docs.spacelift.io/integrations/source-control/raw-git).

- It is one-way: no webhooks, no PR handling, no checks **[D]**.
- Settings are the URL, the repository name (filled from the URL), the branch, project root, project globs and Git checkout **[D]**. In Terraform: `raw_git { namespace, url }`, where `namespace` is cosmetic and `url` is an HTTPS URL **[S]** (`terraform-schema.json`).
- New commits are picked up only when the user presses **Sync**, which moves the tracked commit, and then **Trigger** **[D]**.
- Raw Git cannot use a VCS agent **[D]** [vcs-agent-pools](https://docs.spacelift.io/concepts/vcs-agent-pools).
- No credentials field exists, so only public repositories work **[I]** (from the schema and the page's wording).

### 11.2 What an event becomes

1. An event is matched to every stack and module whose repository and integration it concerns **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#webhook-integrations).
2. Project root filtering applies first for modules: a tag must touch a file under the module's project root, or the module's push policy is skipped and no sample is recorded **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#tag-driven-terraform-module-release-flow).
3. Each stack or module's push policy decides `track`, `propose` or `ignore` (report 09). With no policy attached, the default behaves as: track when a changed file is under the project root or matches an additional glob and the push is to the tracked branch; propose when such a file changed in a push or a PR diff; ignore otherwise and ignore every tag push **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#default-git-push-policy).
4. `track` sets the stack's head commit and creates a tracked run; `propose` creates a proposed run; module tracked runs create module versions, with `module_version` from the policy when set **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy).
5. Runs from the same commit SHA and run type are deduplicated per stack, so a push and a PR event for one commit create one run. The first event wins, which is usually the push event without PR data **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#deduplicating-events). Proposed runs from a `/spacelift` comment bypass deduplication **[D]** [pull-request-comments](https://docs.spacelift.io/concepts/run/pull-request-comments).
6. Runs created by one event are capped by `vcsEventTriggeredRunsLimit` ([section 2.5](#25-browsing-and-testing)) **[D]**.
7. For a mergeable GitHub PR, the run checks out the potential merge commit rather than the head **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#push-and-pull-request-events).
8. Pull requests from forks are ignored unless the push policy's `allow_fork` rule permits them. `head_owner` means the fork's owner on GitHub, the group on GitLab, the project UUID on Azure DevOps, the workspace on Bitbucket Cloud and the project key on Bitbucket Data Center **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#allow-forks).
9. All stacks' policy evaluation for one event has a 10-minute total budget; past it, no action is taken for the event **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy).

Ignored pushes on tracked branches are listed in an **Ignored runs** tab and as a warning on the stack, kept for 7 days, Starter+ tier only. Reasons: change outside the project root; tag push; default push policy disabled with no custom policy; a custom policy dismissed the commit **[D]** [ignored-triggers](https://docs.spacelift.io/concepts/run/ignored-triggers).

A tracked run created when a PR is merged is attributed to the commit, like a push-created run, and reports `vcs/commit` in `TF_VAR_spacelift_run_trigger` **[RN]** (2026-09-09). Runs started from the GitHub check view's **Deploy** button have `triggered_by` of the form `github/<username>` **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#pr-pre-merge-deployments).

### 12.1 VCS check modes

|---|---|

`VCSCheckOptions` and `VCSCheckOptionsInput` **[G]**, added on 2026-06-09 **[RN]**:

| Field | Type | Effect |
|---|---|---|
| `individualFailuresOnly` | `Boolean!` on `VCSCheckOptions`, `Boolean` on the input | Individual checks are sent only when a run ends in a non-success terminal state |

The Terraform provider v1.57.0 exposes `vcs_checks` but not the options **[S]** (`terraform-schema.json`).

Aggregated checks (Business plan and above) post three checks per commit **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#aggregated-checks):

| Check | Groups |
|---|---|
| `spacelift/tracked` | Tracked runs |
| `spacelift/proposed` | Proposed runs |
| `spacelift/modules` | Module runs |

The same three names are documented for GitLab, Bitbucket Cloud, Bitbucket Data Center and Azure DevOps **[D]**. The individual check's name is not documented in the mirror *(unverified; the per-stack name format is unknown)*.

### 12.2 What checks report

- Proposed runs send commit statuses through their phases: in progress while initializing, success with or without changes, and failure **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#commit-status-notifications).
- On GitHub the status links to a check view with changed resources and Infracost data. It offers **Preview** (a proposed run on that commit) and **Deploy** (a tracked run on that commit). A plan policy can deny tracked runs whose trigger starts with `github/` to stop deploys from GitHub, or the stack's `githubActionDeploy` can be turned off **[D]** **[G]**.
- Checks can be required in branch protection so PRs cannot merge without a successful proposed run **[D]**.
- Ignored pushes send no check by default, to avoid noise in monorepos. The push policy's `notify` rule sends one. An ignored push's check is `skipped` unless the policy's `fail` rule sets `failed`, and `message` customizes the text. Both apply only when no run is created **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#status-checks-and-ignored-pushes).
- When an event would exceed the run cap, the reason appears in the VCS as a failure **[D]** [run](https://docs.spacelift.io/concepts/run#limit-runs).

### 12.3 Pull request comments

| Mechanism | How | Source |
|---|---|---|
| Stack label `feature:add_plan_pr_comment` | Comments the plan result on PRs | **[D]** [pull-request-comments](https://docs.spacelift.io/concepts/run/pull-request-comments#via-stack-label) |
| Notification policy `pull_request` rule | Targets a PR by `id`, `commit` or `branch`, with an optional `body` and a `deduplication_key` that edits one comment for the PR's lifetime (report 19) | **[D]** [notification-policy](https://docs.spacelift.io/concepts/policy/notification-policy#pull-request-notifications) |
| GitLab built-in | Each merge request affected by a commit gets a comment with the change | **[D]** [gitlab](https://docs.spacelift.io/integrations/source-control/gitlab#commits-and-merge-requests) |

`pull_request_id` reaches the notification policy only when the run came from the PR event, which deduplication usually discards in favour of the push event; the docs show a push policy that ignores PR-less pushes to keep it **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#pull-request-id-availability).

### 12.4 Deployments and environments

**GitHub.** A tracked run creates a GitHub Deployment marked pending when planning finds changes and the run goes to unconfirmed or starts applying. Discarding the run or a failed apply marks it failure; a successful apply marks it active. The environment name is the stack name; the stack label `ghenv:<name>` overrides it and `ghenv:-` disables deployments **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#deployment-status-notifications). The vcs-agent's GitHub allowlist includes create, list and delete deployment and create deployment status **[S]** [github_enterprise.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/allowlist/github_enterprise.go#L28-L55).

**GitLab.** Each stack has a GitLab Environment where tracked runs are reported **[D]**. The GitLab allowlist covers create, list, stop and delete environment and create and update deployment **[S]** [gitlab.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/allowlist/gitlab.go#L47-L82).

Bitbucket Cloud, Bitbucket Data Center and Azure DevOps have no documented deployment reporting **[D]**.

### 12.5 Pull requests in Spacelift

The stack's PRs tab lists open PRs against the tracked branch, each with its status and most recent run; it is read-only and a PR leaves the list when closed **[D]** [github](https://docs.spacelift.io/integrations/source-control/github#pull-requests). The schema returns up to 50 open PRs **[G]**.

## 13. Push policy interplay

The push policy (report 09) is the only place that turns a VCS event into runs. What this report needs from it:

| Push policy input or rule | Relation to VCS events **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#data-input-schema) |
|---|---|
| `push` | The pushed commit, or for PR events the head or merge commit: `affected_files` (all files touched by every commit in the push, false positives possible), `affected_stacks_count`, `author`, `branch`, `created_at`, `hash`, `message`, `tag` |
| `pull_request` | Null for plain pushes. `action` is one of `opened`, `reopened`, `closed`, `merged`, `edited`, `labeled`, `synchronize`, `unlabeled`, and `commented` for comment events **[D]** [pull-request-comments](https://docs.spacelift.io/concepts/run/pull-request-comments). Also `action_initiator`, `affected_stacks_count`, `approved`, `author`, `base`, `head`, `closed`, `comment`, `diff`, `draft`, `head_owner`, `id`, `labels`, `mergeable`, `title`, `undiverged` |
| `vcs_integration` | `id`, `name`, `provider` (`AZURE_DEVOPS`, `BITBUCKET_CLOUD`, `BITBUCKET_DATACENTER`, `GIT`, `GITHUB`, `GITHUB_ENTERPRISE`, `GITLAB`), `description`, `is_default`, `space`, `labels`, `created_at`, `updated_at` |
| `in_progress` | Queued, ready or unconfirmed runs, for `cancel` |
| `track`, `propose`, `ignore` | Outcome; any `ignore` wins; no match means ignore |
| `notrigger` | Moves the head commit without a run |
| `cancel` | Pre-empts in-progress runs of the same type, best effort |
| `notify`, `fail`, `message` | Commit check for ignored pushes |
| `allow_fork` | Admits fork PRs |
| `module_version` | Module version from the event, usually the tag |

`approved` and `mergeable` differ by provider **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy#approval-and-mergeability):

| Provider | `approved` | `mergeable` |
|---|---|---|
| GitHub, GitHub Enterprise | At least one approval and the repository's minimum met | No conflicts and branch protection satisfied |
| GitLab | At least one approval; all required approvals when approvals are required | No conflicts, blocking discussions resolved, required approvals made |
| Azure DevOps | At least one approving review, including approved with suggestions | No conflicts and blocking policies approved. `undiverged` is always `false` for fork PRs |
| Bitbucket Cloud | At least one approval from someone other than the author | No conflicts |
| Bitbucket Data Center | At least one approval from someone other than the author | No conflicts |

Push policies are a paid feature **[D]** [push-policy](https://docs.spacelift.io/concepts/policy/push-policy). When a push policy does not track a push, the stack's head commit stays behind the branch until the user syncs it **[D]**.

### 14.3 Token

### 14.4 Protocol

The agent is a gRPC client of one service **[S]** [privatevcs.proto](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/privatevcs.proto#L18-L56):

| Element | Shape |
|---|---|
| Service | `Gateway.Connect(stream Response) returns (stream Request)`: a bidirectional stream opened by the agent, on which the gateway sends requests and the agent answers |
| `Request` | `id`, and one of `httpRequest` (`path`, `method`, `headers` map, `body` bytes) or `pingRequest` |
| `Response` | `id`, and one of `error` (string), `httpResponse` (`status` int64, `headers` map, `body` bytes) or `pingResponse` |
| Stream metadata | `vcs-agent-pool-ulid`, `vcs-agent-key`, and `vcs-agent-metadata` (JSON of the `SPACELIFT_METADATA_*` variables) **[S]** [privatevcs.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/privatevcs.go#L3-L10) |
| Transport | TLS 1.2 minimum, or plaintext with `--dial-insecure` **[S]** [agent.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/agent/agent.go#L76-L81) |

Request handling **[S]** [agent.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/agent/agent.go#L147-L235):

1. The agent joins `--target-base-endpoint` (trailing slash removed) and the request path, then copies the headers. The gateway therefore supplies the VCS credentials in the headers; the agent holds none **[I]**.
2. For GitHub Enterprise tarball paths (`/<owner>/<repo>/legacy.tar.gz/<ref>` without a `/codeload` or `/_codeload` prefix), it prefixes the host with `codeload.` to support subdomain isolation **[S]** [codeload.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/codeload.go#L12-L51).
3. With `--http-disable-response-compression` it sets `Accept-Encoding: identity`.
4. The validation strategy may block the request; a block returns an `error` response.
5. The request runs with a 25-second timeout. Only the first value of each response header is returned, and the whole body is buffered. Each request is logged as JSON with id, pool, method, path, status and elapsed time.
6. A ping is answered with an empty `pingResponse`.

Concurrency: the agent keeps `--parallelism` streams (default 4), each serving one request at a time. A stream that ends is replaced after a 5-second pause **[S]** [main.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/cmd/spacelift-vcs-agent/main.go#L281-L322). A misconfiguration error cancels the agent; other errors go to Bugsnag unless disabled **[S]** [main.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/cmd/spacelift-vcs-agent/main.go#L358-L368).

### 14.6 What it proxies: request validation

The docs say the agent applies a strict allowlist of the paths Spacelift needs **[D]**. At the pinned commit the strategy starts as an empty blocklist, which lets every request through, and is replaced only when `--use-allowlist` is true or `--blocklist-path` is set **[S]** [main.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/cmd/spacelift-vcs-agent/main.go#L204-L221). Neither flag is in the command's `Flags` list **[S]** [main.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/cmd/spacelift-vcs-agent/main.go#L140-L153), so urfave/cli v3 does not parse them: passing either on the command line fails as an undefined flag, their environment variables are never read, and the lookups at L206 and L213 see them unset **[I]** (from urfave/cli v3's flag lookup; the library source is not in the local sources). The agent built from this commit therefore validates nothing, and `--allowed-projects` has no effect. The docs are the higher source by the README's precedence, so the conflict is recorded; what a released agent does is *(unverified against a running agent)*.

Blocklist: YAML with `version` and `rules`, each rule a unique `name`, a `method` regex and a `path` regex; a request matching any rule is blocked **[S]** [list.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/blocklist/list.go#L14-L68), [rule.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/blocklist/rule.go#L10-L47).

Allowlist: a fixed table of named calls per vendor; a request matching none is blocked, except on Azure DevOps, where unmatched requests pass as `Unknown Request`. The project captured from the path must match `--allowed-projects` **[S]** [list.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/allowlist/list.go#L31-L61), [azure_devops.go](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/privatevcs/validation/allowlist/azure_devops.go#L77-L107). ### 14.7 Workers and the gateway

- VCS agents serve the Spacelift backend only. Workers download source directly, so a pool needs private workers with network access to the VCS **[D]**.
- Each worker maps pool names to real endpoints with `SPACELIFT_PRIVATEVCS_MAPPING_NAME_<n>` and `SPACELIFT_PRIVATEVCS_MAPPING_BASE_ENDPOINT_<n>`, numbered from 0 **[D]** [vcs-agent-pools](https://docs.spacelift.io/concepts/vcs-agent-pools#configure-direct-network-access).
- Distribution: Linux x86_64 and aarch64 binaries on `downloads.spacelift.io` with SHA256SUMS and a GPG signature (key fingerprint `175FD97AD2358EFE02832978E302FB5AA29D88F7`); other platforms on GitHub Releases; multi-arch image `public.ecr.aws/spacelift/vcs-agent` **[D]**. GoReleaser builds windows, linux and darwin for amd64 and arm64 with FIPS 140 mode (`GOFIPS140=latest`) **[S]** [.goreleaser.yaml](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/.goreleaser.yaml#L4-L12). The image runs as UID 1983 on an Alpine FIPS base **[S]** [Dockerfile](https://github.com/spacelift-io/vcs-agent/blob/553aba3b3e54/Dockerfile).
- Helm chart `vcs-agent` 0.3.0: `credentials.token`, `credentials.endpoint`, `credentials.vendor`, or `credentials.existingSecret` with configurable key names; image tag `latest` by default; `vcsagent.extraEnv` and `envFrom` for the other settings **[S]** [values.yaml](https://github.com/spacelift-io/spacelift-helm-charts/blob/4e02e1d22e73/vcs-agent/values.yaml).
- Self-hosted Spacelift runs a VCS Gateway service behind its own load balancer and DNS name; agents connect to it over gRPC on 443 with TLS terminated at the balancer, and the server and drain reach it over HTTP inside the cluster **[D]** [deploying-to-eks](https://docs.spacelift.io/self-hosted/latest/installing-spacelift/reference-architecture/guides/deploying-to-eks#vcs-gateway-service).

## 15. Self-hosted differences

- Self-hosted has no Marketplace app; GitHub needs a custom app, and the page says a GitHub Enterprise account is needed **[D]** [self-hosted github](https://docs.spacelift.io/self-hosted/latest/integrations/source-control/github).

## What this means for infraweave

- A provider abstraction with seven external source kinds plus native repos, each with its own credentials (App key, project token, email and API token, username and PAT, organization PAT), webhook authentication (HMAC signature, shared token header, basic auth) and API surface.
- One default integration per provider in the root space, any number of space-scoped ones, admin-only secrets, integrations that move between spaces, deletion that detaches stacks rather than failing, and webhook URLs derived from an immutable name.
- Inbound webhook endpoints per integration, with secret rotation, a test operation that reports connection, permission, webhook and app-event checks, and per-event run caps.
- Event normalization into one push or pull request input for the push policy (report 09), with per-provider meanings of `approved`, `mergeable`, `undiverged` and `head_owner`, run deduplication by SHA and run type, fork handling, comment commands and superseded-run cancellation.
- Outbound feedback: per-stack and aggregated checks with failure-only and skip-unchanged options, check actions that start runs, PR comments with edit-in-place keys, and deployment and environment reporting on GitHub and GitLab.
- A private-network path: a gateway that accepts outbound agent streams, a request and response envelope over gRPC, pool tokens and reset, request validation, and worker-side endpoint mapping.
- Source download by archive or by Git checkout, with sparse checkout and the GitHub potential merge commit.
- REST resources for every operation in sections 2 to 14, which the GraphQL API spreads across per-provider mutations with inconsistent names (`webhookURL` against `webhookUrl`, V1 and V2 Bitbucket Cloud inputs).

## Inferred and undocumented

- Webhook signature schemes for GitHub, GitLab and both Bitbucket products are the providers' standard ones; Spacelift's verification code is not public **[I]**.
- The built-in GitHub App uses installation tokens like the custom app **[I]**.
- The VCS agent carries no VCS credentials; the gateway adds them as request headers **[I]** (from the agent copying gateway headers onto every request and having no credential settings).
- `GitHubAppStatus` values show the app check runs through the agent **[I]**.
- GitHub PR comments go through GitHub's GraphQL API **[I]**.
- The check view's Preview and Deploy buttons are GitHub check run requested actions, delivered by the Check run event **[I]**.
- The individual check name format, whether GitLab comment events are processed, whether the `feature:enable_git_checkout` label still has effect, how Bitbucket Cloud writes statuses with read-only token scopes, and the current organization-rename behaviour are *(unverified)*.
- At the pinned commit the vcs-agent cannot enable its allowlist or blocklist, because neither flag is registered, so it validates nothing; this contradicts the docs' strict allowlist *(unverified against a running agent)*. That unregistered flags read as unset is **[I]** from urfave/cli v3's behaviour.
- `BLOB` and `ORIGIN` sources are undocumented; only the schema and the Terraform provider describe them.
