# 0024: Expression language

Status: Accepted

## Context

A person using Spacelift writes in many languages, and they fall into three
audiences.

- **Data shaping, written by users.** Each surface has its own syntax:
  - blueprint and template bodies use `${{ … }}` expressions, which are CEL
    rendered on the server by Spacelift's `celplate`
    ([17 section 6](../reference/17-blueprints-and-templates.md#6-the-expression-engine));
  - output references map an upstream output onto a downstream input
    ([18 section 4.5](../reference/18-scheduling-drift-dependencies.md#45-output-references));
  - notification text is built inside Rego and returned as strings
    ([09 section 3.9](../reference/09-policies.md#39-notification),
    [19 section 3](../reference/19-events-notifications-audit.md#3-the-notification-policy));
  - workflow command templates in `.spacelift/workflow.yml` are Go
    `text/template` strings with fixed parameters, rendered on the worker
    ([20 section 3.2](../reference/20-vendors.md#32-commands-per-phase));
  - environment variable values interpolate `${NAME}` on the worker
    ([13 section 2](../reference/13-configuration.md#2-environment-variables));
  - Flows expressions are JavaScript run in Node.js on agents
    ([23 section 3.4](../reference/23-flows.md#34-expressions-and-event-data)).
- **Decisions, written by users.** Rego policies
  ([09](../reference/09-policies.md), decision
  [0009](0009-policy-engine-opa.md)).
- **Infrastructure code.** Hooks and tasks in the run container
  ([07 section 2.4](../reference/07-stack-model.md#24-hooks),
  [08 section 5](../reference/08-run-lifecycle.md#5-phases-and-hooks)), the
  IaC itself ([20](../reference/20-vendors.md)), Flows app code
  ([23 section 7](../reference/23-flows.md#7-the-app-sdk-contract)) and
  plugins ([25 section 2.7](../reference/25-other-integrations.md#27-execution-in-a-run)).

The published Flows templates show what flow authors write
([23 section 3.7](../reference/23-flows.md#37-expressions-in-the-published-templates)):
most expressions read a field, build a value or compare, a small share are
multi-step functions, and the rest rely on Node.js (dynamic imports, X.509
parsing, `Math.random`, `crypto.randomUUID`) and on TypeScript syntax the
docs do not mention. Nothing makes them deterministic, and all of them run
on agents.

infraweave needs one answer for every user-facing surface that shapes data:
a language users learn once, that the console can check while they type,
that runs safely inside infraweave without a sandbox, and that keeps the
line between what users write and what runs on workers and agents.

## Decision

### Three groups

| Group | Language | Runs in | Surfaces |
|---|---|---|---|
| Expressions | CEL, through cel-go | infraweave's server process modes (below) | Flows input and static configuration, output customization and Transform; blueprint and template bodies; output references; notification text; environment interpolation; workflow command templates |
| Policies | Rego (decision [0009](0009-policy-engine-opa.md)) | The policy engine | Every policy type, including notification routing |
| Infrastructure code | Whatever the user chooses | Workers and Flows agents | Hooks, tasks, the IaC, Flows apps ([0018](0018-flows-runtime.md)) |

No other user-facing language exists. Cron with an IANA timezone and
doublestar globs stay as the standard mini-languages they are
([0022](0022-api-errors-and-update-semantics.md)).

### Two forms

- **Expression.** A whole value. Its result keeps its CEL type. In a flow
  definition it is a YAML value tagged `!expr`; in the definition's JSON
  form it is the object `{"$expr": "<source>"}`. In a blueprint or template
  body, a scalar that is exactly one `${{ … }}` is an expression, as
  Spacelift's bodies already behave
  ([17 section 6.1](../reference/17-blueprints-and-templates.md#61-syntax-and-functions)).
- **Text template.** A string with embedded expressions, `${{ … }}`, rendered
  into text. `$${{` renders a literal `${{`, the escape Spacelift documents for
  bodies generated by Terraform's `templatefile`. In a flow definition an
  untagged string that contains `${{` is a text template.
- **Rendering values into text.** A string is inserted as it is; an integer,
  double or boolean as CEL's `string()` gives it; a timestamp in RFC 3339;
  a duration as CEL's `string()` gives it; a list or map as compact JSON
  with sorted keys; `null` as the empty string.
- **Each field's form is fixed** by its schema. The served OpenAPI
  document marks such fields with `x-infraweave-expression: expression` or
  `template`, so clients and the editor know which form a field takes.

### Surfaces and their variables

| Surface | Form | Variables | Evaluated |
|---|---|---|---|
| Flows input configuration | Expression or text template | `outputs`, `signals`, `secrets`, `now`; `stored` in Memory Set; `items` and `group` in Collect's `emit` | `scheduler`, per event |
| Flows static configuration and app installation configuration | Expression or text template | `signals`, `secrets` | `serve` at save; `scheduler` again when a referenced signal changes |
| Output customization | Expression | `raw` (the block's own output), `outputs`, `now` | `scheduler`, per emitted event |
| Transform | Expression or the steps form (below) | `outputs`, `steps`, `now` | `scheduler`, per event |
| Blueprint and template bodies | Text template; a whole-value template is an expression | `inputs`, `maps`, `context` as in [17 section 6.2](../reference/17-blueprints-and-templates.md#62-context-variables) | Where the operation runs: `serve` for a synchronous create, `scheduler` for a queued deployment change |
| Output references | Expression, optional on a reference | `value` (the referenced output), `outputs` (the upstream stack's outputs) | `serve`, at the downstream run's handover |
| Notification text | Text template in every string a notification policy returns, and in the default messages | `event` (the event document of [0015](0015-events-notifications-webhooks-audit.md)), `logs(phase)` | `scheduler`, in the delivery job |
| Environment interpolation | Text template in a variable's value | `env` (the run's other variables), `run`, `stack` | `serve`, at the run's handover ([0008](0008-run-execution-and-worker-protocol.md)) |
| Workflow command templates | Text template, shell-quoted (below) | `planFileName`, `lock`, `refresh`, `targets`, `workspaceName` | The runner, at initialization |

- **Flows variables.** `outputs.<block>` holds each upstream block's output
  on the event's primary lineage, keyed by the block's camelCase name, as
  [23 section 3.4](../reference/23-flows.md#34-expressions-and-event-data)
  records. `signals.<block>.<signal>` reads a lifecycle block's signals.
  `secrets.<KEY>` reads a project secret. The `ref("signal.…")` helper
  that Spacelift's scenarios use is not offered: `signals.` covers it.
- **Output references** without an expression inject the output as it is,
  which is Spacelift's behaviour. With one, the expression's result is
  injected, and a change in the result, not in the output, decides whether
  the downstream run triggers. A result that reads a sensitive output is
  sensitive.
- **Notification text.** The notification policy still decides what is
  sent and where. Each string it returns (a Slack `message`, an inbox
  `title` or `body`, a webhook `payload` string, a pull request `body`) is a
  text template rendered against the event. `logs(phase)` returns the last
  65,536 bytes of that phase's log, as 0015 describes.
- **Environment interpolation.** A value containing `${{ env.OTHER }}` is
  rendered on the server when the run is handed over, against the
  variables the run resolves to. A value that reads a secret is itself a
  secret: sealed, write-only and masked
  ([0013](0013-secrets-at-rest.md)). `${NAME}` without braces is passed
  through untouched, so the shell in a hook expands it as usual.

### Multi-step logic

The language stays CEL; multi-step logic is built from five parts.

- **Locals.** `cel.bind(name, init, body)` names an intermediate value.
- **A curated function library**, the same on every surface:

  | Area | Functions |
  |---|---|
  | Core | CEL's standard functions, operators and macros (`all`, `exists`, `exists_one`, `map`, `filter`), and optional values (`?.`, `[?]`, `orValue`, `hasValue`) for defaults |
  | Strings | cel-go's strings extension: `charAt`, `indexOf`, `lastIndexOf`, `lowerAscii`, `upperAscii`, `replace`, `split`, `join`, `substring`, `trim`, `format`, `quote`, `reverse` |
  | Lists | cel-go's lists extension: `slice`, `flatten`, `distinct`, `sort`, `sortBy`, `first`, `last`, `range`; two-variable comprehensions (`transformList`, `transformMap`, `transformMapEntry`) |
  | Maps | Comprehensions over keys, `transformMap`, and infraweave's `merge(a, b)`, `pick(m, keys)` and `omit(m, keys)` |
  | Regular expressions | `matches`, and cel-go's regex extension: `regex.extract`, `regex.extractAll`, `regex.replace` (RE2 syntax) |
  | Encoding | `base64.encode`, `base64.decode`; infraweave's `url.encode`, `url.decode`, `url.query(map)`, `json.encode`, `json.decode` |
  | Maths | cel-go's math extension: `math.greatest`, `math.least`, `math.ceil`, `math.floor`, `math.round`, `math.abs`, `math.sign` |
  | Time and durations | `timestamp`, `duration`, their arithmetic and comparisons, and the getters with an optional IANA zone; the `now` variable |
  | Randomness | infraweave's `random.uuid()`, `random.int(min, max)` and `random.string(length)`, drawn from the evaluation's seed |
  | Errors | infraweave's `fail(message)` |

  Functions marked infraweave's are written in Go in `internal/platform/expr` and
  listed, with their signatures, by the completion endpoint. The library
  is versioned with the release; a function is never removed or changed
  in meaning within a major version.
- **`fail(message)`** stops the evaluation with `message`. In Flows the
  delivery fails and the event goes to the block's `errorHandler`
  ([23 section 4.4](../reference/23-flows.md#44-errors)); elsewhere the
  operation fails with `422 validation-failed` naming the field
  ([0022](0022-api-errors-and-update-semantics.md)), or the run fails at
  initialization for a workflow template.
- **Named expressions per Flows project.** A project holds named
  expressions, each with a name, typed parameters, a result type and a
  body. Any expression in the project's flows calls one as
  `fn.<name>(args)`. A named expression may call only named expressions
  that do not call it back, directly or indirectly, so evaluation always
  terminates. Saving one type-checks every flow that calls it, and a change
  that breaks a caller is refused with the callers listed.
- **The steps form for Transform.** A Transform's configuration is one
  expression or an ordered list of steps. Each step has a `name` and an
  `expr`; a step reads `outputs` and the steps before it as
  `steps.<name>`; the last step's value is the block's output:

  ```yaml
  config:
    steps:
      - name: failed
        expr: outputs.runs.items.filter(r, r.state == "FAILED")
      - name: names
        expr: steps.failed.map(r, r.stack.name)
      - name: summary
        expr: '{"count": size(steps.names), "stacks": steps.names.join(", ")}'
  ```

  Step names are unique camelCase identifiers, at most 32 steps.

Anything beyond these is a Go app block ([0018](0018-flows-runtime.md)).
There is no Script block and no second user-facing language.

### Determinism

- **Fixed context.** `now` and a 64-bit random seed are part of every
  evaluation's context. In Flows they are fixed when an event is first
  processed and stored with its delivery, so a retry, a manual retry or a
  replay evaluates the same values. For a blueprint stack creation or a
  template deployment change they are fixed when the change is first
  rendered and stored with its change record, and the `context.time` and
  `context.random_*` values of
  [17 section 6.2](../reference/17-blueprints-and-templates.md#62-context-variables)
  derive from them.
- **Ordered maps.** infraweave's type adapter iterates JSON objects in
  sorted key order, so a comprehension's result never depends on Go's map
  order.
- **No I/O.** No function reads the network, the file system, the clock or
  a random source. The only clock and randomness are `now` and the seed.

### Evaluation and limits

- **Where.** Expressions evaluate in infraweave's server process modes, in
  the code path of the surface (table above). Flows expressions evaluate in
  `scheduler`, where their queue jobs run, except static configuration,
  which `serve` checks at save. Workers, launchers and Flows
  agents never see an expression: an agent receives a block's evaluated
  configuration. The one exception is the workflow command template, which
  the runner renders (below).
- **Secrets** resolve on the server. Only secrets an expression names with a
  literal key (`secrets.KEY` or `secrets["KEY"]`) are loaded; a computed
  secret name is a type error. A value derived from a secret is masked in
  logs, errors and event views by 0013's masker.
- **Cost.** Every evaluation runs with cel-go's runtime cost limit,
  `expressions.cost_limit` (default 1,000,000 units), and is interrupted at
  `expressions.timeout` (default 1 s). An evaluation over either limit fails
  as `fail` does, with a message naming the limit. Source is at most
  `expressions.max_source` (default 16 KiB), and a result at most
  `expressions.max_result` (default 1 MiB).
- **Compiled once.** A compiled program is cached by the hash of its source,
  surface and declared types, so per-event evaluation never parses.

### Type-checking at save

- **Typed context.** Each surface declares its variables with types.
  `outputs` and `signals` come from the output and signal schemas of
  upstream blocks: core blocks' schemas, Flows apps' schemas from their
  `Describe` result ([0018](0018-flows-runtime.md)), and the event kind
  schemas of [0015](0015-events-notifications-webhooks-audit.md) for
  Deploy event triggers. `inputs` comes from a blueprint's or template's
  input definitions; `event` from the event kind.
- **JSON Schema to CEL.** A type provider in `internal/platform/expr` maps an object
  schema with properties to a CEL object type with those fields, arrays to
  lists, and a schema without properties, or with
  `additionalProperties`, to a map of `dyn`. A misspelt field of a known
  object is an error at save.
- **Diagnostics.** Saving a flow, a named expression, a blueprint, a
  template version, a policy's notification text, a variable or a stack
  dependency reference type-checks every expression in it. An error refuses
  the save with `422 validation-failed`, each error naming the field path,
  the line and column, and the message. Warnings (a `dyn` that reaches a
  typed input, a static cost estimate over the limit) are returned with a
  successful save.

### Editor intelligence

The console, `infraweavectl` and the provider use the same Go endpoints, so
every client reports the same diagnostics:

| Operation | Path | Does |
|---|---|---|
| Check | `POST /expressions/check` | Parses and type-checks one expression or text template for a surface and a context (a flow block and input, a template, a stack); returns diagnostics with ranges, the result type and a static cost estimate |
| Complete | `POST /expressions/complete` | Returns completion items at a cursor: variables, fields from the typed context, functions with signatures, named expressions |
| Evaluate | `POST /expressions/evaluate` | Evaluates against sample data or a stored event the caller can read, with `secrets` replaced by masked placeholders, under the same limits; the workbench for expressions |
| Check policy | `POST /policies/check` | Parses and compiles a Rego body with 0009's preamble and returns diagnostics with ranges; simulation stays `policySimulatev2` |

Flows calls the same operations of the one served document, naming a flow
block as the context, so Flows has no copies of them under
`/api/v1/flows/`. Each operation authorizes as a read of its context.
`infraweavectl` exposes them as `infraweavectl expr check`, `complete` and
`eval`, and the provider calls Check during plan for flows, blueprints and
templates.

### Workflow command templates

- **File.** `.infraweave/workflow.yml` holds the nine keys of
  [20 section 3.2](../reference/20-vendors.md#32-commands-per-phase); each
  value is a text template.
- **Variables** are the fixed run parameters, renamed to CEL identifiers:
  `planFileName`, `lock`, `refresh`, `targets` (a list) and
  `workspaceName`. No other variable, no secret and no `now` or randomness
  is in scope, so rendering needs nothing the worker does not already hold.
- **Rendered by the runner** at initialization with the same `internal/platform/expr`
  package and library. Every key is parsed and type-checked before the
  first command runs; a missing key, a syntax error or a type error fails
  the run at initialization, as Spacelift's validation does.
- **Automatic shell quoting.** The template's literal text is shell; every
  interpolated value is quoted for POSIX `sh` (single quotes, with embedded
  single quotes escaped). A list renders as one quoted word per element. No
  function emits unquoted text, so a workspace name or target can never
  become shell syntax. The built-in plan command is
  `terraform plan -input=false -lock=${{ lock }} -out=${{ planFileName }} ${{ targets.map(t, "-target=" + t) }}`,
  with `-refresh=false` added when `refresh` is false.

## Rationale

- **CEL fits what users write.** In the Flows template corpus, about 88% of
  expressions read a field, wrap a constant, build an object or a string,
  compare, default or do arithmetic, which CEL expresses directly
  ([23 section 3.7](../reference/23-flows.md#37-expressions-in-the-published-templates)).
  The multi-step functions are mostly message bodies and Transforms, which
  `cel.bind`, the steps form, named expressions and the library cover. What
  remains (X.509 parsing, dynamic imports) is infrastructure code and
  belongs in an app block.
- **One language across Deploy and Flows.** Spacelift's blueprints and
  templates already use CEL through `${{ }}` on the server
  ([17 section 6](../reference/17-blueprints-and-templates.md#6-the-expression-engine)).
  Adopting it for every data-shaping surface means a user who writes a
  template body can write a Flows input, a notification message and a
  workflow command.
- **Checked while editing.** CEL is statically typed against declared
  variables, so the console flags a misspelt field or a wrong type before
  save, from the same schemas that drive autocomplete. JavaScript's types
  are inferred at best, and Spacelift's own templates resort to
  `Object(outputs)` and `as any` to step around them.
- **Safe in-process.** CEL has no loops beyond bounded comprehensions, no
  I/O and a cost model, so an expression runs in the server with a limit
  rather than in a sandboxed runtime on an agent. That is what lets secrets
  stay on the server and agents never see expressions. Kubernetes runs
  user CEL in its API server on the same grounds, with per-expression cost
  limits.
- **Deterministic.** Fixing `now` and the seed per event makes retries and
  replays reproduce, which Flows' effectively-once emission
  ([0018](0018-flows-runtime.md)) and template rollback need. Spacelift's
  templates are deterministic only without random inputs
  ([17 section 6.2](../reference/17-blueprints-and-templates.md#62-context-variables)).
- **Go-native.** cel-go is Google's Go implementation, Apache-2.0, with the
  extensions the library needs; nothing outside the Go toolchain and its
  gate is added.
- **Rejected: JavaScript or TypeScript.** It needs a Node.js runtime on
  agents and a sandbox per evaluation, cannot be type-checked against block
  schemas without a TypeScript toolchain in the server, is not deterministic
  (`Date`, `Math.random`, async imports) and invites infrastructure code
  into a field meant for a formula. It would also keep a second language
  beside the CEL blueprints already use.
- **Rejected: a Starlark Script block.** Starlark is deterministic and has a
  Go implementation, but it is a second user-facing language with its own
  semantics, and a Script block becomes the place infrastructure code
  hides. The 12% of multi-step expressions do not need it.
- **Rejected: expr (expr-lang).** Go-native and fast, but a single
  implementation without a specification or a portable cost model, and
  unrelated to what Spacelift's blueprints already use.
- **Rejected: jq.** Strong for reshaping JSON, but untyped, awkward for
  building text, and unfamiliar to most authors of a message or a command.
- **Rejected: Rego for expressions.** Rego is built to decide over documents;
  returning a shaped value or a string is awkward, and it has no type-check
  against a block's schema. It stays the policy language
  ([0009](0009-policy-engine-opa.md)).
- **Rejected: Lua.** A general-purpose, untyped language; it needs its own
  sandbox and would be a second language.
- **Rejected: Go `text/template` for workflow commands.** It is untyped,
  differs from every other surface, and cannot quote values for the shell
  automatically, so a crafted workspace name or target could inject shell
  syntax.
- **Departure from Spacelift:** Flows expressions are CEL, not JavaScript;
  Spacelift flow definitions do not import without rewriting their
  expressions.
- **Departure from Spacelift:** `.infraweave/workflow.yml` uses `${{ }}`
  text templates with shell quoting, not Go templates.
- **Departure from Spacelift:** environment interpolation is
  `${{ env.NAME }}`, rendered on the server; `${NAME}` is left to the shell.
- **Departure from Spacelift:** blueprint and template context time and
  random values are fixed per rendered change, so re-rendering reproduces
  them.
- **Departure from Spacelift:** strings a notification policy returns are
  text templates, and `logs(phase)` replaces the `spacelift::logs::*`
  placeholders.
- **Departure from Spacelift:** output references may carry an expression.

## Constraints

- **The runner exception.** The workflow command template is the one
  expression surface evaluated on a worker, because the file lives in the
  run's source. Its variables are only run parameters the worker already
  holds.
- **Celplate's exact library is unknown.** Spacelift's blueprint engine
  names cel-go's string extensions but not its version
  ([17 section 6.1](../reference/17-blueprints-and-templates.md#61-syntax-and-functions)).
  A blueprint body that uses a function outside infraweave's library fails
  type-checking at save, naming the function.
- **Cost units are cel-go's.** The default limit is chosen so that the
  largest template expression in the corpus, rewritten in CEL, costs well
  under it; the acceptance fixtures pin that.
- **Schema quality bounds checking.** A block output declared without
  properties is `dyn`, and expressions over it are checked only at run
  time.
- Code placement is decision 0004's: the engine is
  `internal/platform/expr` and the editor endpoints are the `expressions`
  domain.

## Verification

- `TestUnitExprLibrary` covers every library function, including its
  error cases, and fails when the completion endpoint's function list and
  the registered functions differ.
- `TestUnitExprTemplates`: rendering of every CEL type into text, `$${{`
  escapes, whole-value templates keeping their type.
- `TestUnitExprDeterminism` evaluates `now`, every `random.*` function and
  a map comprehension twice with the same context and requires identical
  results.
- `TestUnitExprCostLimit` and `TestUnitExprTimeout`: an unbounded
  comprehension over a large list fails with the limit named.
- `TestUnitExprSchemaTypes` maps JSON Schema fixtures to CEL types and
  checks that a misspelt field is a save-time error.
- `TestUnitWorkflowQuoting` renders targets and workspace names containing
  quotes, spaces, `$()` and newlines, and runs the result through `sh -n`
  and `sh -c 'printf %s\n "$@"'` to prove each value stays one word.
- `test/acceptance/features/expressions_flows.feature` (`@postgres`,
  `@flows-agent`): a Transform in the steps form, a named expression, a
  `fail` routed to a Handle Error block, a retry reproducing `now` and
  `random.uuid()`.
- `test/acceptance/features/expressions_editor.feature` (`@postgres`):
  Check, Complete and Evaluate against a flow and a template, and a save
  refused with diagnostics.
- `test/acceptance/features/expressions_deploy.feature` (`@postgres`,
  `@tofu`): a custom workflow template with a hostile workspace name, an
  interpolated environment variable reading a secret and staying masked,
  an output reference with an expression, and a notification message
  template.
