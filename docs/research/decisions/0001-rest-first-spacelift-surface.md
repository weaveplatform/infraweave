# 0001: The REST API and infraweave's own SDK, CLI and provider

Status: Accepted

## Context

infraweave offers Spacelift's capabilities as self-hosted software, with
Spacelift as the reference foundation rather than an interface to copy.
Spacelift exposes its capabilities through GraphQL: 285 queries and 380
mutations on a single endpoint. Users reach that API through Spacelift's own
clients: spacectl, the official Terraform provider, and for Flows `flowctl`
and `terraform-provider-flows`
([05](../reference/05-terraform-provider.md),
[06](../reference/06-spacectl-and-clients.md),
[23 sections 11 and 12](../reference/23-flows.md#11-flowctl)).
infraweave has to choose its own API style and say how users reach it before
any feature work begins.

## Decision

### The API

- **infraweave's public API is REST over JSON, described by OpenAPI 3.**
  infraweave serves no GraphQL endpoint, no GraphQL facade and no
  compatibility facade for any Spacelift client. Spacelift's clients do not
  work against infraweave unchanged.
- **Spacelift's schema stays the functional reference.**
  `api/reference/spacelift/spacelift.openapi.yaml` gives a REST route for every
  Spacelift root field, generated by the rules in
  [02](../reference/02-graphql-to-rest-mapping.md). infraweave's own spec is
  scaffolded from it family by family and may diverge from it, with each
  divergence recorded.
- **Divergence is recorded in the parity baseline.** `specref parity`
  (`make parity`) matches the served document's operations with the
  reference's by `operationId` and route, ignoring path parameter names, and
  files each reference operation under its tag as present, moved (its
  `operationId` at another route, or its route under an `operationId` the
  reference lacks) or missing; a served operation that matches none is
  infraweave-only. `api/parity-baseline.json` lists the missing operations
  by tag and each moved one with the reason for the move, so a deliberate
  divergence, such as a renamed route, is a moved entry whose reason says
  why. Decision [0003](0003-api-conventions.md)'s conventions change
  shapes, not identities, so they are not divergence. The baseline only
  shrinks: `TestUnitDeployParity` fails on an operation the baseline does
  not accept, on a move without a reason, and on an entry the comparison no
  longer needs, which `make parity-baseline` removes.
- **Every client is built on the same API.** The SDK, the CLI, the provider
  and the console call the served REST API and nothing else; no client has a
  private route.
- **Surfaces outside the parity surface.** The deploy document also serves
  the `Organization` tag, the organization admins' API for accounts,
  members, identity providers, account limits and usage
  ([0021](0021-capability-scope-and-supersession.md)), which has no
  Spacelift counterpart. The operator API is a document of its own (0021).

### Names

- **No infraweave name says Spacelift.** No operationId, path, tag, schema,
  property, enum value, header, parameter, environment variable,
  configuration key, file name, metric, policy input key or command that
  infraweave serves or reads contains "spacelift" in any case. Spacelift's
  names appear only in the reference under `api/reference/spacelift/`, in
  the `x-` extensions that map a served name back to it (`x-graphql`,
  `x-bruno`, `x-terraform`), in mapping tables such as the one below, and in text that
  describes Spacelift.
- **No name says root but the installation's.** Root is the installation's
  top node ([GLOSSARY](../../../GLOSSARY.md)). An account's top space is
  addressed by the account's slug, and Spacelift's root admin is the account
  admin ([0007](0007-authorization-spaces-and-roles.md)).
- **Reference names keep their meaning.** Spacelift's account is
  infraweave's account, so reference names that say account
  (`accountUpdateAuthorizationScheme`, `/account/...`) are served as they
  are. A served name that says organization means the glossary's
  organization, so a reference name that uses the word for an account is
  renamed.
- **No served text says Spacelift.** A served description, summary or
  example says infraweave where it describes infraweave's behaviour and links
  no Spacelift page. A family scaffolded from the reference arrives with
  Spacelift's descriptions, and its pull request rewrites them, because the
  served document is what infraweave's SDK, provider and console docs are
  generated from. `TestUnitServedNames` reads every served string outside
  the mapping extensions.

### Rename table

The rename register, [`docs/data/renames.json`](../../data/renames.json),
is the one list of reference names that infraweave serves or reads under
another name; records that rename a name cite it rather than repeat it. An
`identifier` record names one reference name, where `*` stands for any run
of characters, and its replacement, and `TestUnitServedNames` reads those
records; a `schema` member limits the record to that schema's property or
enum value. A `concept` record names a reference concept in words. The
records that own the renamed behaviour are 0006 (the AWS account ID, the
session channel, the token file), 0007 (admins and the top space), 0008
(run variables and the config element category), 0009 (the policy input),
0010 and 0012 (environment variables, the `INFRAWEAVE` provider, the
comment command), 0017 (metrics), 0018 (Flows), 0019 (AI), 0022 and 0024
(repository files).
`BillingTierFeature` is not served, so its values are mapped to feature
names rather than renamed; decision 0021's mapping table covers
`SPACELIFT_INTELLIGENCE` with the rest.

### SDK: `pkg/sdk`

infraweave's SDK is the Go package `pkg/sdk` together with the generated
clients it wraps.

- **Generated client.** `make generate` produces one oapi-codegen client per
  served bundle, `pkg/client/<spec>` (`pkg/client/deploy` from
  `api/deploy.openapi.yaml` today), and `make verify-generate` fails on any
  drift. `pkg/sdk` wraps these packages rather than replacing them: the
  generated code stays mechanical, drift-checked and outside the coverage
  gate, the hand-written layer stays small and inside it, and one SDK client
  spans every served document (Deploy and Flows) with one credential and one
  transport. The generated packages stay public, but `pkg/sdk` is the
  supported entry point.
- **Hand-written layer.** `pkg/sdk` adds what every client needs and the
  generator cannot express:
  - **API key to token exchange.** An API key ID and secret, or an OIDC API
    key, are exchanged at `POST /auth/token`
    ([0006](0006-authentication-and-tokens.md)); the SDK caches the JWT and
    exchanges again before `validUntil`. A ready token, such as the in-run
    token in `INFRAWEAVE_API_TOKEN`, is used as is.
  - **`Idempotency-Key` on writes.** Every `POST` and `PATCH` carries a key
    ([0003](0003-api-conventions.md)), generated once per call and reused on
    each of its retries.
  - **Retries on `429`.** The SDK waits for `Retry-After` and retries, bounded
    by the caller's context; `503` responses that carry `Retry-After` are
    treated the same way.
  - **Pagination iterators.** List operations are exposed as Go iterators that
    follow `nextCursor` (0003) until the list ends.
  - **Typed problem errors.** Every `application/problem+json` response
    becomes a typed error keyed by its slug
    ([0022](0022-api-errors-and-update-semantics.md)), so a caller tests for
    `not-found` or `invalid-state` with `errors.As`, never by matching text.
- **Names.** SDK services follow the served spec's tags, and types and
  fields follow the names Spacelift's provider uses after the rename table
  above, so the SDK, the CLI and the provider read alike.
- **Go only.** Other languages can be generated later from the same served
  bundle; the console's TypeScript client is generated that way.
- **Boundary.** `pkg/sdk` imports nothing under `internal/`, as for
  `pkg/client/`, so other repositories can depend on it without pulling in
  server code.

### CLI: `infraweavectl`

- **A separate binary.** `cmd/infraweavectl` builds `infraweavectl`, which is
  not a process mode of `infraweave`. It calls the API only through
  `pkg/sdk`.
- **Command tree.** Its command tree mirrors spacectl's: `stack`, `module`,
  `policy`, `provider`, `workerpool`, `blueprint`, `template`, `audit-trail`,
  `run-external-dependency`, `ai`, `profile`, `registry`, `whoami`, `version`
  and `api`, with the subcommands and capabilities that
  [06 section 8](../reference/06-spacectl-and-clients.md#8-what-an-infraweave-cli-must-cover)
  lists. Flows commands, mirroring `flowctl`'s, sit under one `flows` group.
  Commands for surfaces Spacelift's CLI lacks, such as the operator's
  organization and tier management and the organization admins' account
  management ([0021](0021-capability-scope-and-supersession.md)), sit in
  groups of their own. `infraweavectl api` sends any REST request and
  prints the served OpenAPI document.
- **MCP.** `infraweavectl mcp` proxies stdio to the hosted `/mcp` surface
  with the CLI's credentials and adds no tools of its own
  ([0019](0019-ai-provider-boundary.md)).
- **Configuration.** cobra and viper, with strict YAML profiles and the
  credential rules of [0021](0021-capability-scope-and-supersession.md);
  browser login uses the `INFRAWEAVECTL` session channel (0006).

### Provider: `weaveplatform/terraform-provider-infraweave`

- **Repository.** The Terraform and OpenTofu provider lives in its own
  repository, `weaveplatform/terraform-provider-infraweave`, because the
  public registries only publish a provider from a public repository named
  `terraform-provider-<name>` in lowercase. Its source address is
  `weaveplatform/infraweave`.
- **Built on the SDK.** The provider calls the API only through `pkg/sdk`,
  imported at a pinned version of this module. It is built with the Terraform
  plugin framework and serves protocol 6.
- **Names.** Resources, data sources and attributes mirror Spacelift's
  provider with an `infraweave_` prefix in place of `spacelift_`
  (`spacelift_stack` becomes `infraweave_stack`), with the rest of the
  rename table applied to attribute names, and import IDs keep the
  shapes [05](../reference/05-terraform-provider.md#what-this-means-for-infraweave)
  records. Provider settings mirror Spacelift's (`api_key_endpoint`,
  `api_key_id`, `api_key_secret`, `api_token`) with `INFRAWEAVE_` environment
  variables.
- **One provider for Deploy and Flows.** Flows resources sit in the same
  provider, named `infraweave_flows_<name>` after `terraform-provider-flows`'s
  `flows_<name>`, so they share one configuration and one credential.
- **Parity oracle.** `api/reference/spacelift/terraform-schema.json` stays the
  parity oracle: every Spacelift resource and attribute has an infraweave
  equivalent or a recorded reason why not, checked as
  [0016](0016-testing-and-acceptance.md#the-terraform-provider-parity-oracle)
  sets out. The Flows resources are held to the `terraform-provider-flows`
  operations that [0018](0018-flows-runtime.md) maps.

### Console

The console is another client of the same API, with no route of its own.
Decision 0023 records its design.

## Rationale

- **REST suits infraweave better.**
  - It gives standard HTTP caching, status codes, per-route authorization
    and rate limits.
  - It is debuggable with curl.
  - It integrates directly with chi, oapi-codegen and the rest of the
    weaveplatform toolchain.
- **GraphQL's main benefit doesn't apply.** Client-shaped queries matter for
  a rich UI with varied views. Spacelift's own provider and spacectl use a
  fixed set of selections.
- **Mechanical generation keeps the fidelity.** Generating REST from the
  schema keeps Spacelift's types, nullability and descriptions. Coverage can
  be shown complete instead of hand-maintained.
- **One SDK under every client.** Token exchange, idempotency, retries,
  pagination and problem handling are written and tested once. They replace
  the token handling, rate-limit handling and not-found text matching that
  [05 section 3](../reference/05-terraform-provider.md#3-provider-configuration-and-transport)
  records in Spacelift's provider. Retrying a write is safe only because each
  carries an `Idempotency-Key`.
- **Mirroring Spacelift's names.** Users moving from Spacelift rewrite a
  configuration by renaming a prefix rather than relearning a model, and the
  parity check compares like with like. The names are infraweave's own
  through the prefix, so no Spacelift name or alias appears in infraweave's
  surfaces.
- **No Spacelift name on a served surface.** A served name is infraweave's
  contract with its own clients. A name that says Spacelift would present
  infraweave's behaviour as Spacelift's, and since no Spacelift client works
  against infraweave, keeping it buys no compatibility. Renaming only where
  a name says Spacelift, says root for an account's top space, or says
  organization for an account keeps every other reference name, so
  migration stays a rename of a few names from one table.
- **One table, checked against the bundle.** A rename recorded only in the
  record that makes it is easy to miss when a family is scaffolded; one
  table that a test reads catches a scaffolded name the moment it is
  bundled.
- **One provider, not two.** Spacelift ships Flows as a separate product with
  its own login and its own provider. infraweave's Flows shares the account,
  identity and API with Deploy (0018), so a second provider would only
  duplicate configuration.
- **Rejected: a GraphQL-compatible server or a compatibility facade.** Either
  would let Spacelift's clients run unchanged. It would also bind infraweave
  to Spacelift's schema evolution, to GraphQL tooling and to the RPC shapes of
  the Flows clients indefinitely.
- **Rejected: the provider in this repository.** The registries' naming rule
  requires a repository of its own, and a separate release cycle lets a
  provider fix ship without an infraweave release.

## Constraints

- **Spacelift clients won't work against infraweave.** spacectl, the official
  Terraform provider, `flowctl`, `terraform-provider-flows` and the Bruno
  collection can't talk to it. Migration from Spacelift is a data import and a
  change of client, not a client re-point.
- **The provider follows the SDK's releases.** A provider release pins one
  version of this module, so an API change reaches Terraform users only after
  `pkg/sdk` ships it and the provider updates its pin.
- **Creating the provider repository** is outside this record.

## Verification

Implemented:

- `make verify-reference` checks that the committed reference is exactly what
  the snapshots generate, and that it validates as OpenAPI 3.0.3.
- `test/acceptance/features/spec_reference.feature` checks that every root
  field is accounted for and that no mutation is RPC-shaped, and checks the
  core collections, ids moved from inputs into paths, and auth.
- `make verify-generate` fails when `pkg/client` differs from what the
  served bundle generates.
- `TestUnitServedNames` (`api/deploy_test.go`) fails when any key or string
  of the served deploy bundle outside the mapping extensions, descriptions
  and enum descriptions included, contains "spacelift" in any case; when a
  path, tag, operationId, schema, property, enum value, parameter or header
  name matches an identifier record of the rename register; or when a
  record's infraweave name says spacelift. A fixture that serves the property
  `spaceliftAwsAccountId` and a description that names Spacelift proves
  that both checks reach what they claim to read, and its `x-terraform`
  value proves that the mapping extensions pass.
- `TestUnitDeployParity` (`api/parity_test.go`) fails when a reference
  operation is neither served unchanged nor accepted by
  `api/parity-baseline.json`, and when a baseline entry is no longer needed.
  `TestUnitDeployParityChecks` proves it against the committed documents:
  removing a served path names its operations, serving a listed operation is
  an improvement until the baseline is rewritten, and a moved path passes
  once its reason is recorded.

Planned:

- `pkg/sdk` unit tests against a chi test server cover the token exchange and
  re-exchange, idempotency keys reused across retries, `Retry-After`
  handling, iteration across pages, and one typed error per slug; a test
  fails when the SDK's slugs differ from 0022's registry.
- The CLI and provider checks of [0016](0016-testing-and-acceptance.md):
  one `cli_<area>.feature` per row of report 06 section 8, and schema parity
  and behaviour scenarios for the provider.
