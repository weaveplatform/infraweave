# 0001: A REST-first surface for the Spacelift feature set

Status: Accepted

## Context

infraweave reproduces Spacelift's feature set as self-hosted software.
Spacelift exposes that feature set only through GraphQL: 285 queries and 380
mutations on a single endpoint. infraweave has to choose its own API style
before any feature work begins.

## Decision

- **infraweave's public API is REST over JSON, described by OpenAPI 3.**
  infraweave serves no GraphQL endpoint and no GraphQL facade.
- **Spacelift's schema stays the functional reference.**
  `api/reference/spacelift/spacelift.openapi.yaml` gives a REST route for every
  Spacelift root field, generated by the rules in
  [02](../02-graphql-to-rest-mapping.md). infraweave's own spec is scaffolded
  from it family by family and may diverge from it, with each divergence
  recorded.
- **Clients are infraweave's own.** That means a REST-native Terraform
  provider and, when needed, a CLI.

## Rationale

- **REST suits infraweave better.**
  - It gives standard HTTP caching, status codes, per-route authorization
    and rate limits.
  - It is debuggable with curl.
  - It integrates directly with chi, oapi-codegen and the rest of the
    weaveplatform toolchain.
- **GraphQL's main benefit doesn't apply.** Client-shaped queries matter for
  a rich UI with varied views. Spacelift's own provider and spacectl use a
  fixed set of selections.
- **Mechanical generation keeps the fidelity.** Generating REST from the
  schema keeps Spacelift's types, nullability and descriptions. Coverage can
  be shown complete instead of hand-maintained.
- **Rejected: a GraphQL-compatible server.** It would have let the official
  Spacelift provider and spacelift-api-bruno run unchanged. It would also
  have bound infraweave to Spacelift's schema evolution and to GraphQL
  tooling indefinitely.

## Constraints

- **Spacelift clients won't work against infraweave.** spacectl, the official
  Terraform provider and the Bruno collection can't talk to it. Migration
  from Spacelift is a data import, not a client re-point.

## Verification

- `make verify-reference` checks that the committed reference is exactly what
  the snapshots generate, and that it validates as OpenAPI 3.0.3.
- `test/acceptance/features/spec_reference.feature` checks that every root
  field is accounted for and that no mutation is RPC-shaped, and checks
  the core collections, ids moved from inputs into paths, and auth.
